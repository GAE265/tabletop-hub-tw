# MR 審核指南

> 給所有組員。被指定為 Reviewer 時，照這份文件審核。規則以 `AGENTS.md` 為準。

## 審核者的責任

按下 Approve 代表：**「我看過了，我同意這些程式進到 `dev`。」**
如果只看 CI 是綠的就核准，等於沒有審核。CI 只能檢查測試和格式，檢查不了「做的事情對不對」。

## 一、在 GitHub 上審核的步驟

### 1. 收到通知
被選為 Reviewer 時，GitHub 會寄信，也會出現在右上角的通知鈴鐺。點進 MR 頁面。

### 2. 先讀說明（Conversation 分頁）
- 這個 MR 要做什麼？
- **情境表格**：MR 說明裡一定會有「情境／操作／預期結果」表格（`AGENTS.md` 7.4）。情境是否合理？有沒有漏掉的狀況？
  - 用 OpenSpec 的人，表格是從 spec 整理出的摘要，想看完整規格，到 MR 說明寫的 `openspec/changes/<變更名稱>/specs/` 查看。
  - 沒有這張表格的 MR，先請作者補上再審。
- **是否動到契約**（API、資料表、MQTT 訊息）？有的話要特別仔細看。
- 頁面下方的 CI 是否全部綠勾。**CI 沒過，先不用審，請作者修好再說。**

### 3. 看程式（Files changed 分頁）
- 左側檔案清單可以收合資料夾，**先看測試，再看實作**：測試告訴你它要做到什麼，實作告訴你它怎麼做到。
- 看完一個檔案，勾右上角的「Viewed」，那個檔案會收起來，下次只會顯示有變動的部分。
- 自動產生的檔案可以略過，例如：`uv.lock`、`pubspec.lock`、`*.g.dart`、`*.freezed.dart`，以及 `flutter create` 產生的平台資料夾。

### 4. 留意見
- 滑鼠移到某一行的行號，會出現藍色「+」，點下去就能針對那一行留言。
- 想直接建議怎麼改，留言時按工具列的「±」（Insert a suggestion），作者可以一鍵套用。
- **留言時選「Start a review」，不要選「Add single comment」**。這樣所有意見會一次送出，作者不會被通知轟炸。

### 5. 送出審核結果
看完後，按右上角綠色的「Review changes」（或「Finish your review」），三選一：

| 選項 | 什麼時候用 |
|---|---|
| **Approve** | 沒問題，可以合併。也可以附上不影響合併的小建議 |
| **Request changes** | 有必須修改的問題，改好才能合併 |
| **Comment** | 只有問題想問，還不確定要不要改 |

### 6. 作者修改後
作者推新的 commit 後，回到 Files changed，只會顯示你上次看完之後的變動。確認問題都處理了，再按 Approve。

## 二、審核時要看什麼

依序檢查，前面的比後面的重要：

**1. 測試案例**
- [ ] 正常、輸入錯誤、沒有權限、狀態衝突四種情況都有嗎？
- [ ] 測試程式真的在驗證那些測試案例嗎？（拿測試案例和 `tests/` 裡的測試程式對照）
- [ ] **有沒有既有測試被修改或刪除？** 有的話，MR 說明裡要寫出理由（`AGENTS.md` 7.5）。
- [ ] 情境表格標「（本機）」的測試，MR 說明有附上本機執行的指令、通過數量與日期嗎？這類測試 CI 不會跑（`AGENTS.md` 7.6）。

**2. 秘密與資料**
- [ ] 沒有任何金鑰、密碼、連線字串寫在程式裡？
- [ ] 沒有規則書全文或店家真實資料？

**3. 分層規則（`AGENTS.md` 第 4、5 節）**
- [ ] 後端：router 沒有寫 SQL 或商業邏輯；service 沒有 import FastAPI；權限檢查寫在 service。
- [ ] 前端：頁面沒有直接呼叫 API，邏輯寫在 `state/`。
- [ ] 沒有改到別人的 domain；有的話，MR 說明有寫原因並 @ 對方。

**4. 契約**
- [ ] API 路徑符合 RESTful 規則（名詞複數、不放動詞）。
- [ ] 錯誤回應用統一格式。
- [ ] 命名符合術語表（`AGENTS.md` 第 10 節）。

**5. 看得懂嗎**
- [ ] 你能用一兩句話說出這段程式在做什麼嗎？看不懂就留言問，看不懂本身就是問題。

## 三、各角色的重點

| 審核者 | 特別要看 |
|---|---|
| 瑋鋐 | 有 migration 的 MR：資料表名稱是否以 domain 開頭、主鍵是否為 UUID、**已合併的 migration 有沒有被修改** |
| 立倫 | 動到 API 契約的 MR：路徑、請求與回應格式、錯誤代碼是否一致 |
| 永傑 | 有 `needs-ui` 標籤的 MR：交接說明是否清楚，`state/` 是否足夠讓你做正式頁面 |

## 五、作者要做的事

- MR 說明照範本填完整，特別是測試案例表格。
- 對每則留言回覆：修改了就回「已修改」，不同意就說明理由，不要直接無視。
- 留言處理完，按該則留言下方的「Resolve conversation」。
- 不要自己核准自己的 MR（GitHub 本身也不允許）。
