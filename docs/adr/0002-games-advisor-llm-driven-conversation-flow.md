# games_advisor 的追問與推薦由 LLM 依對話規則決定

games_advisor 的推薦 Agent 每收到玩家一則訊息，就要判斷該繼續追問還是開始推薦。這個判斷交給 LLM：每輪送一份對話規則（`instructions`），並提供一個「查桌遊」工具（function calling）。Agent 認為條件與偏好夠了，就呼叫工具查詢並推薦。程式只負責三道護欄，其他行為都寫在對話規則裡，不寫成程式判斷。立倫選擇讓 Agent 依對話規則自己判斷；這也配合 ADR 0001：條件與偏好每次都完整放在工具參數裡，後端不用另外保存狀態。

三道程式護欄：

1. 工具參數的人數必填。service 收到不合理的人數時，把錯誤回給 LLM。
2. 只推薦工具回傳的桌遊。
3. 玩家每送一則訊息，最多呼叫 2 次工具。

## Considered Options

- **由程式判斷**：每輪 LLM 只做結構化擷取，輸出目前的條件與偏好，service 照固定規則決定追問或推薦，例如缺人數就追問。行為固定，全部能用 pytest 搭配 `FakeLLMProvider` 驗證；但後端不存對話（ADR 0001），條件與偏好要另外找地方保存或每輪重新擷取。沒有選，因為立倫偏好由 Agent 依對話規則判斷。

## Consequences

- 追問時機、最多追問幾輪、找不到時放寬哪個條件、離題處理，都只寫在對話規則裡。同一句話不保證每次都得到一樣的反應。
- pytest 只能驗三道護欄和工具的篩選結果；上面那些行為改由「怎麼驗收推薦結果」用情境題組，拿真的模型檢查。AGENTS.md §7 把測試當成判斷功能做對了沒的唯一標準；情境題組要怎麼放進這個標準，由那張 ticket 提出，再和組員確認。
- `integrations/llm` 的介面要支援 function calling：送出工具定義、收到工具呼叫、送回工具結果，而且整段都要能接上 `previous_response_id`。fake 實作要能模擬工具呼叫。介面由瑋鋐擁有，要另外提案。
- 地端模型對 function calling 的支援程度不一，`LLM_PROVIDER` 切到地端時更難運作。這讓 ADR 0001 偏離 AGENTS.md §4.2 的程度更明顯。
- 玩家每送一則訊息，最多呼叫模型 3 次（2 次工具呼叫，加上最後的回覆），而且每次都會重新計算前面所有輪的輸入 token，選模型與估算課程額度時要算進去。模型要支援 function calling，也要能穩定遵守對話規則。
