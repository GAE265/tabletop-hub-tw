# 主持人能查哪些資料、誰能開主持

Type: grilling
Status: resolved
Blocked by: 08, 16
Map: [AI 語音主持](../map.md)

## Question

主持人回答規則問題時要查資料。已經定案、這張不用再問的事：

- 一場主持不掛戰績的局，主持人不讀 `matches`（「[主持人在一局裡怎麼帶流程](08-host-flow-in-a-match.md)」）。
- 主持人會呼叫的工具有五個：查規則、轉交思考模型、下一步、上一步、結束主持。名稱與參數在 spec 定。
- 獲勝門檻與圓版格數由人數查表得出；魔法之書的效果不解釋；隱藏資訊的規則已定。
- 等待中玩家問了新問題，就取代舊題（「[用 Flash 還是 Plus、要不要轉交思考模型](09-model-lineup.md)」）。

還要決定：

1. 規則從哪裡查。畫地圖時定的是「用 `rules_qa` 已有的規則檢索，不另建規則庫」。之後查到三件事，所以要重新確認：
   - `rules_qa` 的 `service` 目前只有一個問答方法。它自己做檢索，再呼叫一次 LLM 寫出答案，沒有「只回規則片段」的方法。主持人要用它，不是每題多等一次 LLM，就是要請永傑加一個方法。
   - 本機的白薔薇規則全文有雜訊與錯字，圖上的字沒有入庫，永傑與瑋鋐暫不修正。
   - 試聽時主持人查的不是 `rules_qa`，是原型裡一份用自己的話寫的規則摘要（分 9 個主題）。「有查就不會編」的結果，是用這份摘要測出來的。

   選項：
   - a. 照原定，用 `rules_qa` 的檢索。
   - b. `host` 自己帶一份白薔薇的規則摘要（用自己的話寫，不抄規則書）。
   - c. 兩個都用：先查摘要，查不到再查 `rules_qa`。
2. 怎麼確保主持人先查再答。補測時用嘴問 6 題，它只查了 3 題，有 1 題的答案是編的；只要有查，就不會編。選項：
   - a. 指令寫死「凡是規則問題，一律先查」。
   - b. 後端對玩家的每句話都先查一次，把查到的內容直接放進對話。
   - c. 兩個都做。
3. 誰能開主持：三種角色（玩家、店家人員、管理員）都可以，還是要限制。一場主持開了之後，只有開的人能接著主持，還是任何登入的人都可以。沒有權限時回什麼（AGENTS.md §4.5 要求附「沒有權限」的測試案例）。
4. 查不到規則時，主持人怎麼回答。

## Answer

2026-11-21 立倫決定。

### 1. 規則從哪裡查

- 照原定，用 `rules_qa` 的規則檢索（選項 a），拿回**原文片段**。不寫規則摘要，也不把整份原文交給主持人。
- `rules_qa` 加一個方法：把玩家的問題轉成 embedding，在 `rules_qa_chunks` 找最像的幾段，回傳原文片段。不叫 LLM 寫答案。這個方法給其他 domain 的 service 用，不檢查使用者，不開放成 API（比照 `rules_ingest` 的 `read_manual_pages`）。
- 新方法由我們在 `feature/host` 寫，MR 說明寫出原因並 @ 永傑（AGENTS.md §2 第 3 點）。動手前先在群組跟永傑說一聲。
- 理由：主持人自己會組答案，用不到現有問答方法的第二次 LLM。embedding 比的是意思，不是字面，比較不怕語音辨識的錯字（例如「血之陣營」）。
- 代價：每題多一次 Azure 的 embedding 呼叫，多等多久在實作時量。每位組員的資料庫都要先建好 `rules_qa` 的白薔薇索引。

### 2. 先查再答

- 指令寫死「規則問題一律先查」（選項 a）。
- 不用查的：語音指令；「[白薔薇 demo 的主持規則：追加哪些、忽略哪些](23-white-rose-demo-host-rules.md)」定的五類固定回答（魔法之書、問勝負或張數、問推理或打法、問換誰與金幣水晶在誰手上、要它記戰績或算分）。
- 不做「後端對每句話都先查」：閒聊也會被查，而且每句回話都要等檢索做完才能開口。
- 沒有實測過。手動檢查加一項「規則題有沒有先查」。

### 3. 魔法之書與原文缺的地方

- 檢索到的片段有魔法之書的效果時，照常交給主持人，不逐頁排除。指令寫死：問到魔法之書的效果，一律回固定台詞「魔法之書的效果要看書上的說明，我不能為你解釋。」手動檢查加 2 題魔法之書。
- 開主持時，後端在主持人的指令裡補三件事。只放「[對照實體遊戲，補齊白薔薇規則裡讀不到的地方](15-white-rose-rule-gaps.md)」查證過的事，不改寫原文：
  - 這局人數的兩個獲勝門檻。
  - 這局人數的圓版格數。
  - 「瞞刃就是暗刃」。
- 原文的雜訊不補（「[向新善、永傑、瑋鋐確認戰績欄位與規則全文的問題](16-ask-owners-about-matches-and-rules-text.md)」已定暫不修正）。
- 「白薔薇 demo 的主持規則」第 7 節要答得出的五個主題：門檻由上面的補充提供，其餘四個在原文裡查得到（各人數的角色牌組在第 3 頁，常見疑問在第 13 頁）。

### 4. 查不到規則

- 檢索一定會回傳幾段，就算都不相關。「查不到」由主持人看完片段後自己判斷。
- 查不到時，主持人說（固定回答的第六句，草稿）：「很抱歉，我手上的規則沒寫到這個。請翻一下規則書，或大家商量決定。」不猜，不轉交思考模型。
- 片段裡有相關的規則，但要推理才答得出：照「[用 Flash 還是 Plus、要不要轉交思考模型](09-model-lineup.md)」轉交思考模型（已定）。
- 規則索引還沒建好時，照常開主持。新方法回空的結果，主持人照查不到處理，問規則一律回這句。

### 5. 誰能開主持

- 玩家、店家人員、管理員都能開。沒登入回 401（`core/` 已做好）。
- 開了之後，連上主持人、接著主持、切換接話方式、結束主持，只有開的人和管理員能做。別人回 403 `PERMISSION_DENIED`（`core/` 現成的錯誤；比照訂位與戰績的「本人或管理員」）。
- 例子：換一支手機、用同一個帳號登入，可以接著主持；換別人的帳號，只能重新開一場。
- 一個人同一時間只有一場主持。再按「開始主持」，舊的那場直接結束（就是頁面上的「重新開始」），不回 409。
- 同一場主持同一時間只連一支手機。後連上的取代先連的，先連的那支顯示「已在別的裝置接著主持」。
- 理由：每一條連線都在用阿里雲的額度；首版後端只有一台。
