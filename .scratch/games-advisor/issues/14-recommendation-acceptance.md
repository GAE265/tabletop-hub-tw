# 怎麼驗收推薦結果

Type: grilling
Status: resolved
Blocked by: 07, 10
Map: [桌遊推薦 Agent + 桌遊 RAG](../map.md)

## Question

1. 自動化測試（pytest 加 `FakeLLMProvider`）要驗什麼：條件篩選、追問流程、錯誤處理。
2. 推薦品質用什麼方式評估：自訂的玩家情境題組、「符合全部條件」與「符合部分條件」分開計分、人工檢查。
3. 題組要幾題、放在哪裡（不得含心得原文）。

## Answer

2026-11-08 與立倫 grilling 定案（3 輪）。

**總覽**

推薦結果分兩層驗收：

- **pytest**：用假的 LLM，進 CI，是合併的唯一標準（AGENTS.md §7）。
- **評估題組**：用真的模型和真的資料，手動跑，不進 CI、不擋合併，用來看推薦品質。

這個功能主要是展示 Agent 與桌遊 RAG 的應用，準確率不追求最高。只有 Demo 題要求全部通過。

**1. pytest 的範圍**

- 前面 ticket 留在本張 Comments 的項目全部加起來：工具篩選與護欄、排序、心得管線、推薦卡片檢查、API 狀態碼。這張不另外增加項目。
- 補上留言漏掉的一層：repository（SQL 篩條件、pgvector 取心得片段）與匯入指令，連 CI 內建的 PostgreSQL 測試，比照現有的 seed 測試。資料用自己編的假桌遊。
- service 照 §7.5 用假的 repository。

**2. 名稱**

- 用真的模型檢查的題目叫 **評估題組**，裡面每一題叫 **評估題**。前面 ticket 寫的「情境題組」都是指它。
- 不用「情境題組」，因為 §7 測試表格的「情境」欄指的是 pytest 的測試案例，組員看 MR 時會搞混。
- 這是開發流程用語，只寫進 spec，不放進 `GLOSSARY.md`。

**3. 評估題組在團隊流程的位置**（要向組員提議）

- pytest 仍然是合併的唯一標準。評估題組不進 CI，也不擋合併，原因有三個：CI 沒有 Azure 金鑰（§2.1）、每次跑都花課程額度、模型每次的反應不一定一樣。
- MR 改到下面任何一項時，立倫手動跑一次，把分數摘要貼在 MR 說明，放在 §7.4 的表格外面：對話規則、工具定義、模型部署、標籤詞彙表、排序設定。
- 這個做法並不難改回來，所以不另寫 ADR。ADR 0002 的 Consequences 已經補一句連到這裡，等組員看 ADR 0002 時一起確認。

**4. 怎麼執行**

- 寫成後端指令，和其他批次指令放在一起：`uv run python -m app.domains.games_advisor.<模組> <題組檔路徑> --out <報告路徑>`。
- 在本機開發資料庫上執行。先跑完匯入桌遊與心得管線，用真的 15 款桌遊、標籤與向量，連真的 Azure。
- 指令在後端內部直接呼叫 service，不經過 HTTP API，因為 API 回應裡沒有工具參數。真的 LLM provider 外面包一層記錄器，記下每次呼叫模型的內容和回應。
- 沒有採用 pytest 標記：結果會時紅時綠，§7.2 又不准用 skip 掩蓋失敗，還要改共用的 pytest 設定。
  - 2026-11-10 補充：「[AGENTS.md 加上需要金鑰的測試規則](../../games-advisor-impl/issues/11-agents-md-secret-tests.md)」生效後，「§7.2 不准 skip」和「要改共用的 pytest 設定」兩個理由不再成立（08 會加上 `real` 標記；後來定名為 `external`，已由 #18 註冊，見 AGENTS.md 7.6）。評估題組仍然寫成指令，不寫成 pytest：結果時紅時綠，而且它產出的是分數和人工勾選的報告，不是單純的通過或不通過。

**5. 評估題的格式**

一題評估題就是一段對話腳本：幾則立倫寫好的玩家訊息，每則後面寫預期結果。只寫這一輪要檢查的欄位就好。

| 欄位 | 意思 | 程式怎麼比對 |
|---|---|---|
| `action` | `follow_up`（追問）、`recommend`（推薦）、`off_topic`（離題處理） | `recommend` 要有卡片；`follow_up`、`off_topic` 要沒有卡片。這兩種的差別由 `manual` 人工檢查 |
| `tool_args` | 「查桌遊」的工具參數 | 人數、時長、年齡、難度比對數值；標籤、類別、機制、排除清單檢查「有沒有包含」，模型多帶其他偏好不算錯。比對這一輪第 1 次工具呼叫，也就是玩家原本說的條件 |
| `relaxed_constraint` | `playtime`、`age` 或 `null` | 相等 |
| `expect_any` | 人工認為合適的桌遊 | 前 3 款裡至少出現一款 |
| `forbid` | 不能出現的桌遊，例如違反條件或已經推薦過 | 一款都不能出現 |
| `manual` | 人工檢查提示，例如「回覆有說明放寬了時長」 | 報告列成勾選框 |

- 桌遊用 BGG ID 指定，重新匯入時不會變；標籤用詞彙表代碼指定。
- 某一輪不符合預期時，這題就停在那一輪，後面的輪次標成「未執行」。

例子：

```json
{
  "id": "relax-playtime-01",
  "turns": [
    {
      "player": "我們 4 個人，15 分鐘內要玩完，想要歡樂一點的",
      "expect": {
        "action": "recommend",
        "tool_args": {"players": 4, "max_minutes": 15},
        "relaxed_constraint": "playtime",
        "manual": ["回覆有說明放寬了時長"]
      }
    }
  ]
}
```

**6. 計分**

- **條件分**：`action`、人數、時長、年齡、`relaxed_constraint`、`forbid`。這些都有標準答案，錯一個就是推薦錯了。
- **偏好分**：標籤、類別、機制、難度參數，以及 `expect_any`。
- **人工項目**：`manual` 的勾選結果，另外統計，不混進上面兩種分數。
- 每種分數都算通過比例，例如「條件分 38/40」。
- 原本題目寫「符合全部條件」與「符合部分條件」分開計分，改成上面三種：程式已經保證卡片只會來自工具的查詢結果，模型真正會錯的地方是條件抓錯、放寬錯，或偏好沒抓到。

**7. 題目數量與涵蓋範圍**

共 10 題，5 組行為各 2 題，一題可以同時涵蓋好幾種行為：

1. **追問**：沒有人數就只問人數；只講人數時追問偏好並給選項；玩家回「都可以」就直接推薦；最多追問 2 輪。
2. **抓參數**：時長、年齡、口語換算成難度、負面偏好，以及詞彙表對不到的偏好（例如「適合約會」）。
3. **放寬與調整**：先放寬時長、再放寬年齡，最多一項；人數不放寬，改建議分桌；加偏好後排除已推薦的桌遊；改條件後重新查。
4. **推薦理由**：只寫命中的偏好和心得裡的感受；命中負面偏好要說出來；最多 2 句；至少引用 1 段心得片段；`reply` 不列出桌遊名單；用繁中找英文心得片段的效果。
5. **離題與語言**：三種離題處理；玩家用英文問，也用繁中回答。

- 其中 3 題是 **Demo 題**，每款 Demo 遊戲（《血與刃的白薔薇》、《阿不思學院》、《馬可波羅》）一題，算進它涵蓋的那一組。
- 標籤要等詞彙表定好才能寫，所以題目在心得管線跑完後才寫。AI 可以先起草，由立倫審核定稿。

**8. 及格線與次數**

- **Demo 題**：劇本照 Demo 時要講的對話寫，`expect_any` 是那款 Demo 遊戲。各跑 3 次，條件分、偏好分、人工項目 3 次都過才算過。
- **其他 7 題**：每題跑 1 次，只記錄分數，不設及格線。
- 指令提供 `--repeat N` 參數，需要時可以多跑幾次。
- 粗估跑一次的花費：7 題各 1 次加上 Demo 題各 3 次，大約 50 則訊息，輸入約 70 萬 token。用 gpt-4.1-mini 大約 NTD 15 以內，用 gpt-4.1 大約 NTD 50–60。這是用過去公開價格的量級估的；報告會印出實際的 token 用量。

**9. 檔案位置**

- **題組檔**：`backend/tests/games_advisor/eval_cases.json`，用 JSON，不新增 YAML 套件，進 repo。裡面只有立倫自己寫的玩家訊息和預期結果，沒有心得原文（§2.2）。
- **報告**：Markdown，寫到 `--out` 指定的 repo 外路徑，比照心得管線的人工驗證草稿。報告裡有心得片段的原文，所以不進 repo。
- **MR 說明**：只貼三種分數與 token 用量的摘要，不貼回覆內容。

**10. 評估指令本身的 pytest**（進 CI）

- 題組檔的格式檢查：欄位名稱正確、`action` 的值合法、每題都有 `id`。
- 用 `FakeLLMProvider` 照腳本回傳，驗證：
  - 每種預期欄位的比對規則（數值相等、有沒有包含、`forbid`）。
  - 不符合時停下，後面的輪次標成「未執行」。
  - 三種分數的計算。
  - Demo 題 3 次都過才算過。
  - 報告寫到 `--out` 指定的路徑。

**留給其他 ticket 的事**

- 「[專題專用 Foundry 要部署哪些模型](17-foundry-model-deployments.md)」：評估題組跑一次的 token 量級；換模型前後可以各跑一次評估題組比較。
- 「[詞彙表改版或換 embedding 模型時怎麼處理](18-vocabulary-and-embedding-revisions.md)」：評估題用詞彙表代碼指定標籤，詞彙表刪改代碼時，題組檔也要跟著改。
- spec：把 pytest 項目（本張 Comments 加上第 1 點）與評估題組寫進 spec 與 §7 情境表格。

- 2026-11-07（來自「[對話狀態存在哪裡](05-conversation-state.md)」）：後端不存對話，不能從資料庫拿真實對話重跑；真實對話只能在 30 天內用 Azure 的 response id 讀回。
- 2026-11-07（來自「[Agent 怎麼追問、什麼時候推薦](07-conversation-flow.md)」）：pytest 驗工具篩選、人數必填、每則訊息最多呼叫 2 次工具。以下行為由 LLM 判斷，要放進情境題組用真的模型檢查：沒有人數時只問人數；沒提偏好時追問一次並給選項；最多追問 2 輪；查無結果先放寬時長、再放寬年齡，最多一項，且回覆要說出來；人數不放寬並建議分桌；推薦後調整時不再出現推薦過的桌遊；離題的三種處理；一律用繁中回覆。情境題組要怎麼放進 AGENTS.md §7「測試是唯一標準」，見 ADR 0002。
- 2026-11-07（來自「[條件與偏好怎麼比對桌遊](10-matching-strategy.md)」）：pytest（假的 repository、fake embedding）驗：條件篩選、人數 1–30、負面偏好排後面、RRF 合併、沒有偏好時依難度再依名稱、回傳最多 3 款、片段 ID 檢查。情境題組用真的模型檢查：詞彙表對不到的偏好（例如「適合約會」）有沒有影響排序、繁中 `preference_text` 找英文心得片段的效果。
- 2026-11-08（來自「[心得怎麼變成標籤](09-review-to-tags-pipeline.md)」）：管線的 pytest（fake LLM、fake embedding、自行編寫的假心得，依 AGENTS.md §2 規則 2）要驗：心得片段的切法（短段合併、長段切開、長度是設定值）；同步詞彙表的格式檢查與 30 個上限；歸納詞彙表草稿已存在時拒絕覆蓋；上標籤的三項自動檢查與「重試 1 次再跳過」；匯入標籤草稿只允許刪除、只替換草稿裡有的桌遊；每款一個交易、重跑覆蓋、`--bgg-id`；`reviews.json` 有資料庫沒有的 `bgg_id` 時拒絕執行；`below_minimum` 照跑、0 篇沒有輸出。LLM 有沒有照給分標準給分、摘要有沒有只寫感受，pytest 驗不到，靠人工驗證或情境題組。
- 2026-11-08（來自「[推薦理由要寫什麼、要不要附出處](11-recommendation-reasons.md)」）：pytest（fake LLM）驗：這則訊息沒呼叫工具時不出卡片；不在工具結果裡的 `game_id` 整款丟掉；不屬於該款的片段 ID 只丟該 ID；卡片照工具順序排列；全部丟掉時 `reply` 換成固定文字；第 1 次查詢 0 款、第 2 次拿掉或放寬時長或年齡時標出放寬條件；卡片的基本資料與出處來自資料庫。情境題組用真的模型檢查：推薦理由只寫命中的偏好與心得片段裡有的感受、命中負面偏好時有說出來、不寫條件與信心分數、最多 2 句、有心得片段時至少引用 1 段、`reply` 不列桌遊名單。
- 2026-11-08（來自「[需要整合層提供哪些介面](12-integrations-interface.md)」）：pytest 一律用 fake 和 httpx `MockTransport`，CI 不連真的 Azure。真實模型只在兩個地方測得到：第一張實作 ticket（手動驗證 `tools` 加 `text.format`），以及這張的情境題組。`LLMResponse` 帶 token 用量，可以用來估算跑一次情境題組要花多少錢。
- 2026-11-08（來自「[API 契約與 prototype 頁面](13-api-contract-and-prototype.md)」）：API 是 `POST /api/v1/advisor/messages`。pytest 至少要涵蓋：201 的一般回覆與推薦（`relaxed_constraint`、卡片照工具順序、`excerpts` 只有 `id`、`text`、`language`）；422（空白、超過 500 字）；401（JWT 模式未登入）；404 `GAMES_ADVISOR_CONVERSATION_NOT_FOUND`；503 `GAMES_ADVISOR_UNAVAILABLE`（LLM 與 embedding 都算）；500。固定文字兩種（模型拒答、推薦全部被丟掉）回 201 和請求帶來的舊 `response_id`。完整對照表見該 ticket 第 2、3 點。
