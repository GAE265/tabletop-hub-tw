# 推薦理由要寫什麼、要不要附出處

Type: grilling
Status: resolved
Blocked by: 09, 10
Map: [桌遊推薦 Agent + 桌遊 RAG](../map.md)

## Question

1. 每款推薦的理由要包含什麼：符合哪些條件、命中哪些偏好與標籤。
2. 要不要附心得出處（連結或摘錄）；若要附，使用條款允許顯示到什麼程度。
3. 理由由 LLM 產生還是用模板組合；怎麼避免 LLM 寫出資料裡沒有的特性。

## Answer

2026-11-08 與立倫 grilling 定案（2 輪）。

**總覽**

每款推薦是一張卡片，由程式和 LLM 分工：

| 部分 | 內容 | 誰產生 |
|---|---|---|
| 基本資料 | 繁中名稱、人數、時長、年齡、難度 | 程式，從資料庫填 |
| 放寬的條件 | 放寬了哪一項（時長或年齡） | 程式，比對這則訊息的工具呼叫（第 6 點） |
| 推薦理由 | 最多 2 句繁中 | LLM |
| 出處 | 推薦理由引用的心得片段：原文、`title`、`site_name`、`source_url` | LLM 給片段 ID，程式從資料庫補 |

- 程式產生的部分一定正確，可以用 pytest 驗。
- 沒有採用的方案：全部由 LLM 寫成一段文字（數字可能寫錯，程式檢查不了）；全部用模板組合（讀起來生硬，心得片段對不上理由）。

**1. 推薦理由寫什麼**

- 寫：命中的偏好，用中文名稱（標籤用 `games_advisor_tags.name`，BGG 類別與機制由 LLM 翻成中文）；心得片段印證的感受。
- 命中負面偏好時一定要說，例如「有擲骰，運氣成分偏重」。負面偏好只排後面、不排除，被推薦時玩家要知道。
- 不寫：條件（卡片上已有）；信心分數、「幾篇心得提到」；心得片段沒提到的特性。
- 最多 2 句。玩家說「都可以」、沒有命中的偏好時，寫心得片段裡最突出的感受。
- 素材只限工具回傳的命中偏好與心得片段。心得摘要不回傳給 LLM：摘要是 LLM 寫的，沒有出處。
- 以上寫進對話規則，有沒有照做由情境題組檢查。

**2. 引用心得片段**

- 每款推薦帶一個 `excerpt_ids` 清單，最多 2 個；不在句子裡標 [1]、[2]。
- 該款有心得片段時至少引用 1 段（寫進對話規則，程式不強制）。沒有心得片段的桌遊，推薦理由只根據命中的偏好，卡片不顯示出處。
- 卡片只顯示有被引用的片段。
- 沒有採用：工具回傳的 2 段都顯示、LLM 不引用（推薦理由和出處對不起來）。

**3. 出處顯示什麼**

- API 回傳每段被引用片段的完整原文（40–300 字，「[心得怎麼變成標籤](09-review-to-tags-pipeline.md)」的切法）、`title`、`site_name`、`source_url`，顯示成「文章標題 · 網站名稱」並連到原文。畫面要不要摺疊或截斷，由「[API 契約與 prototype 頁面](13-api-contract-and-prototype.md)」決定。
- 心得片段資料表加 `title`（可為空），和 `source_url` 一樣從 `reviews.json` 複製。不加 `published_on`。
- 不加 `author`：AI 助理提過著作權法第 64 條要求明示出處、已知作者時要寫出作者名稱，立倫決定不加。
- 英文片段顯示原文，不翻譯：逐字原文最容易查證，推薦理由本身已是繁中。沒有採用：產生片段時翻譯並存進 `text_zh`（多約 200 次翻譯）；推薦時即時翻譯（查證不了、多花 token）。

**4. 「查桌遊」工具回傳給 LLM 的內容**

每款回傳：

- `id`、繁中名稱、人數、時長、年齡、難度（也用來回答離題規則的「已推薦桌遊的基本資料」）。
- 命中的偏好：標籤給繁中名稱與定義；類別、機制給 BGG 英文名稱；難度有沒有在範圍內。
- 命中的負面偏好，格式同上。
- 心得片段：`id`、`text`、`language`。

不回傳：`title`、`site_name`、`source_url`（LLM 用不到，也避免它在推薦理由裡寫網址）、心得摘要、信心分數。

**5. 最終回覆的格式**

LLM 的最終回覆用 structured outputs（strict JSON schema）：

```json
{
  "reply": "幫你找到 3 款適合 4 人、輕鬆聊天的桌遊。",
  "recommendations": [
    { "game_id": "<uuid>", "reason": "…", "excerpt_ids": ["<uuid>"] }
  ]
}
```

- `recommendations` 最多 3 筆；追問或離題時是空陣列。
- `reply` 不列出桌遊名單，名單只出現在卡片（寫進對話規則，情境題組檢查）。放寬條件時，`reply` 仍要說出放寬了哪一項（「[Agent 怎麼追問、什麼時候推薦](07-conversation-flow.md)」已定）。
- 沒有採用：回覆維持純文字，插 `[[game:uuid]]` 標記再用 regex 解析（容易漏寫、寫錯，沒有 schema 擋）。
- 待驗證：Responses API 的 `text.format` 和 `tools` 是同一個請求裡的不同參數，應該能一起用，但文件沒有直接範例。在 Azure 實際驗證交給「[需要整合層提供哪些介面](12-integrations-interface.md)」。
- 串流時怎麼顯示 `reply`，由「API 契約與 prototype 頁面」決定。

**6. 程式檢查**

這是「Agent 怎麼追問、什麼時候推薦」第 2 道護欄「只推薦工具回傳的桌遊」的做法。後端不存對話（「[對話狀態存在哪裡](05-conversation-state.md)」），service 只看得到這則訊息的工具結果：

1. 這則訊息沒有呼叫工具時，`recommendations` 一律當作空的。玩家追問「剛剛第二款適合小孩嗎？」只用文字回答，不出卡片。
2. `game_id` 不在這則訊息的工具結果裡：整款丟掉。`excerpt_ids` 裡不屬於該款這次回傳片段的 ID：只丟那個 ID。都記 log，不重試、不回錯誤。
3. 卡片照工具回傳的順序排列，由 service 重排，不照 LLM 輸出的順序。
4. LLM 至少推薦 1 款、卻全部被丟掉時，把 `reply` 換成固定文字（例如「這次推薦出了問題，請再說一次你的需求」），並記 log。
5. 放寬的條件：這則訊息第 1 次查詢 0 款，第 2 次查詢拿掉或放寬了 `max_minutes`、`min_minutes`、`youngest_age` 其中一項，就標為放寬。已知限制：上一則訊息已經放寬、這則訊息第 1 次查詢就沒帶該條件時，不會標出；卡片仍顯示實際時長與年齡，接受。

- 沒有採用：每次請求依工具結果動態產生 strict schema，把 `game_id`、`excerpt_ids` 設成 enum（和整合層綁得比較緊，需要的 schema 關鍵字在 Azure 上的支援程度未查證）。

**術語**：`GLOSSARY.md` 提案區新增「推薦理由（reason）」，「推薦」的定義改成「每款附上推薦理由」。「出處」不另立術語，說「推薦理由引用的心得片段」。

**留給其他 ticket 的事**

- 「需要整合層提供哪些介面」：最終回覆要在同一個請求裡同時用 structured outputs 與 tools，並在 Azure 驗證；fake 實作要能回傳符合 schema 的最終回覆。
- 「API 契約與 prototype 頁面」：卡片的回應格式、串流、`reply` 被換成固定文字的情況、出處的摺疊或截斷。
- 「[怎麼驗收推薦結果](14-recommendation-acceptance.md)」：第 6 點的 pytest，第 1、2、5 點的情境題組。
- 「[專題專用 Foundry 要部署哪些模型](17-foundry-model-deployments.md)」：對話模型要在同一個請求裡支援 function calling 與 structured outputs。
- `spec.md`：卡片分工、對話規則裡推薦理由的寫法、程式檢查規則、心得片段資料表加 `title`。

## Comments

- 2026-11-07（來自「[Agent 怎麼追問、什麼時候推薦](07-conversation-flow.md)」）：只能推薦工具回傳的桌遊；推薦結果用什麼格式交給程式檢查，在這張或「API 契約與 prototype 頁面」決定。條件被放寬時（時長或年齡），回覆要明說哪一項沒有符合。BGG 的英文類別與機制名稱，回覆時翻成中文；回覆一律用繁中。
- 2026-11-07（來自「[標籤詞彙表怎麼定](08-tag-vocabulary.md)」）：每個標籤有繁中名稱和一句繁中定義，可以直接用在理由裡；每款的每個標籤有 0–1 的信心分數，理由要不要提到在這張決定。
- 2026-11-07（來自「[條件與偏好怎麼比對桌遊](10-matching-strategy.md)」）：「查桌遊」工具回傳前 3 款，每款附上命中的偏好（標籤、類別、機制、難度）、命中的負面偏好，以及最相近的 2 段心得片段（每段帶片段 ID）。立倫決定理由要用心得片段當出處；service 會檢查 LLM 引用的片段 ID 都在回傳範圍內。這張要決定：理由怎麼引用片段、出處顯示到什麼程度（摘錄、連結）、推薦結果交給程式檢查的格式。
- 2026-11-08（來自「[心得來源走哪條路](16-review-source-decision.md)」）：心得片段帶 `source_url`、`site_name`、`language`，出處可以連回原文。`reviews.json` 另有 `title`、`author`，需要顯示時心得片段資料表要再加欄位。心得來源包括 PTT、中英文部落格、評測網站，片段可能是英文。
- 2026-11-08（來自「[心得怎麼變成標籤](09-review-to-tags-pipeline.md)」）：心得片段資料表的欄位是 `game_id`、`text`、`embedding`、`source_url`、`site_name`、`language`。片段存原文，可能是英文，顯示時要不要翻譯在這張決定；需要 `title`、`author`、`published_on` 時在這張加欄位（目前還沒有 migration）。標籤依據的心得只存在人工驗證用的草稿，不存進資料庫，所以理由的出處只能用心得片段。標籤的繁中名稱與定義存在 `games_advisor_tags`；信心分數 0.5 以上代表至少 1 篇心得明確提到，0.8 以上代表 2 篇以上明確提到。心得摘要是 120–200 字的繁中，描述感受與適合的場合。
