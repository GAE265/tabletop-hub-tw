# 收錄哪些桌遊、存哪些欄位

Type: grilling
Status: resolved
Blocked by: 02, 15
Map: [桌遊推薦 Agent + 桌遊 RAG](../map.md)

## Question

依「桌遊基本資料從哪裡取得」的結論決定：

1. 收錄哪些桌遊、大約幾款，用什麼規則挑選，例如 BGG 排名前 N 名或特定類別。
2. 每款桌遊存哪些欄位，哪些欄位可以當條件篩選。
3. 缺少繁中名稱時怎麼處理。
4. 資料怎麼匯入：一次性指令，從哪個檔案或 API 讀取。

## Answer

2026-11-07 與立倫 grilling 定案。

**1. 收錄 15 款**

挑選規則：只收基本版，不收擴充；繁中名稱一律必填，沒有台灣繁中版就不收，但 Demo 三款不受這條限制；每組都和一款 Demo 遊戲的條件相近，用來測試「只差在偏好」時排序對不對。

- 繁中名稱是暫定，立倫手動填寫時以盒子上的名稱為準，例如阿瓦隆的盒名是「抵抗組織：阿瓦隆」。
- BGG ID 除了農家樂修訂版取自卡牌屋商品頁的 BGG 連結，其餘都已用 Wikidata `P2339` 核對。標「待查」的 3 款由 Codex 用 XML API 的 `search` 查，立倫確認。

**2. 每款存的欄位**

| 用途 | 欄位 | BGG 來源 |
|---|---|---|
| 識別、顯示 | 繁中名稱 | 立倫手填 |
| 識別、顯示 | 原文名稱 | `name type="primary"` |
| 識別、外連 | BGG ID | thing 的 `id` |
| 條件 | 最少人數、最多人數 | `minplayers`、`maxplayers` |
| 條件 | 最短時長、最長時長（分鐘） | `minplaytime`、`maxplaytime` |
| 條件 | 最低年齡 | `minage` |
| 偏好 | 類別（多個，BGG 英文名稱） | `link type="boardgamecategory"` |
| 偏好 | 機制（多個，BGG 英文名稱） | `link type="boardgamemechanic"` |
| 偏好 | 難度 `weight`（1–5） | `statistics` 的 `averageweight` |

- 不存：簡介、圖片、價格、評分與排名、最佳人數。之後比對或推薦理由需要文字時，再由那兩張 ticket 加上。
- 類別、機制、難度來自資料來源，和從心得產生的標籤分開（術語見 `GLOSSARY.md`）。

**3. 資料來源**

- 立倫註冊 BGG 非商業用途的 application 取得 token；Codex 帶 token 呼叫 XML API `thing?id=...&stats=1`，15 款一次請求就能抓完。
- 不抓 BGG 網頁，也不繞過 Cloudflare（map 的固定偏好）；不抓代理商網頁。
- 人數、時長、年齡一律用 BGG 的數字，不和盒子或代理商頁比對。

**4. 匯入（方案 A）**

1. Codex 把欄位寫成 `games.json`，放在 repo 外的團隊資料夾；檔案不進 repo。
2. 後端匯入指令讀這個檔案、檢查欄位，寫入 PostgreSQL。指令比照 `app/dev/seed.py`，用 `python -m` 執行，檔案路徑當參數。
3. 重跑時以 BGG ID 判斷同一款：已存在就更新欄位，UUID 不變；不刪除檔案裡沒有的桌遊。
4. 測試只用 3 款自編的假桌遊。
5. `games.json` 的欄位格式寫進 `spec.md`，Codex 照格式產生。

**沒有採用的方案**

- 立倫看盒子或代理商頁手填所有欄位：改用 BGG 是因為類別、機制、難度只有 BGG 有統一標準。
- Wikidata：熱門款也常缺時長，`zh-tw` 名稱幾乎沒有。
- 後端匯入指令直接呼叫 BGG（方案 B）：要在 `integrations/` 新增 BGG 轉接層，token 也要分給組員。
- Codex 直接產生 SQL（方案 C）：欄位寫錯沒有程式擋，SQL 綁死資料表結構。
- 存最佳人數：不處理。

**不處理的事**

BGG 條款中「能不能存進資料庫、快取能存多久」不再核對，也不另外處理來源標示。立倫表示 BGG 的規定不在他的處理範圍，以完成負責的功能模組為優先。
