# 條件與偏好怎麼比對桌遊

Type: grilling
Status: resolved
Blocked by: 01, 06, 08
Map: [桌遊推薦 Agent + 桌遊 RAG](../map.md)

## Question

決定檢索比對方式：

1. 條件用 SQL 篩選，還是交給向量搜尋。
2. 偏好用標籤比對、向量搜尋，還是兩者混合；分數怎麼合併。
3. 要不要重排序（reranking），用 LLM 還是其他方式。
4. 哪些文字要做 embedding（桌遊說明、標籤、心得摘要）；繁中的玩家需求怎麼命中英文內容。
5. 向量存在 pgvector 的哪些資料表與欄位。

## Answer

2026-11-07 與立倫 grilling 定案（3 輪）。

**總覽**

「查桌遊」工具分三步：

1. 用 SQL 篩條件。
2. 程式算分排序，取前 3 款：負面偏好優先排後面，再用 RRF 合併結構化分數與相似度。
3. 每款取最相近的 2 段心得片段，連同桌遊資料一起回傳給 LLM。

- LLM 照順序推薦，不自己挑。沒有採用：工具只篩條件、由 LLM 排序；程式算分後讓 LLM 自由挑。
- 不另做重排序（reranking）：最終順序已由程式決定。教材的 Cross-Encoder 示範不採用。
- embedding 用在兩處（排序與理由出處），主要目的是展示 RAG 的學習成果。AI 助理提過「15 款不需要向量」，立倫不採用。

**1. 條件：SQL 篩選**

| 條件 | 工具參數 | 符合的桌遊 |
|---|---|---|
| 人數（必填） | `players`，整數 1–30 | `min_players ≤ players ≤ max_players` |
| 時長上限 | `max_minutes` | `max_playtime ≤ max_minutes` |
| 時長下限 | `min_minutes` | `max_playtime ≥ min_minutes` |
| 年齡 | `youngest_age`（最年輕玩家的年齡） | `min_age ≤ youngest_age` |

- 時長上下限都和 BGG 的最長時長比。「90 分鐘內」代表最長的一局也在 90 分鐘內，所以卡坦島（60–120）不符合。
- 人數超出 1–30 時，service 回錯誤給 LLM。12 人這種合理但查無結果的人數，照「[Agent 怎麼追問、什麼時候推薦](07-conversation-flow.md)」建議分桌。
- 排除清單 `exclude_game_ids`（桌遊的 `id`，UUID）也在這一步排除。

**2. 偏好：結構化分數**

| 偏好 | 工具參數 | 命中時加分 |
|---|---|---|
| 標籤 | `prefer_tags`（詞彙表代碼 enum） | 該標籤的信心分數 |
| 類別 | `prefer_categories`（BGG 英文名稱 enum） | 1 |
| 機制 | `prefer_mechanics`（BGG 英文名稱 enum） | 1 |
| 難度 | `weight_min`、`weight_max`（1–5，可只填一個） | 在範圍內加 1 |

- 信心分數低於門檻的標籤，當作這款桌遊沒有這個標籤，正面、負面偏好都一樣。門檻是一個設定值，暫定 0.5，「心得怎麼變成標籤」定好給分標準後再確認。
- 標籤、類別、機制、排除清單的 enum 都從資料庫產生。LLM 負責把「工人放置」轉成 `Worker Placement`。
- 難度是偏好：範圍外不排除，只是不加分。例如「不要太燒腦」是 `weight_max: 2.5`，對話規則提供口語換算的參考值。

**3. 負面偏好：第一排序條件**

- 參數是 `avoid_tags`、`avoid_categories`、`avoid_mechanics`，負面分數的算法同第 2 點。難度不需要負面參數。
- 命中任何負面偏好的桌遊，排在沒命中的後面；都有命中時，負面分數低的在前。
- 負面偏好不進向量比對，因為 embedding 分不出「不要」。
- 沒有採用：和正面同等扣分（命中 3 個正面、1 個「運氣影響大」的卡坦島仍可能排第一）；扣兩倍（倍數沒有根據）。

**4. 偏好：相似度（embedding 用途一）**

- LLM 在工具參數帶 `preference_text`：把所有正面偏好（包括已轉成 enum 的）用繁中寫成一句，例如「想要歡樂爆笑、適合情侶約會」。玩家沒有偏好時不帶。
- service 把 `preference_text` 轉成向量，和每款桌遊的心得摘要向量算 cosine 相似度。
- 詞彙表和 BGG 欄位對不到的偏好（例如「適合約會」）也因此能影響排序。
- 相似度只用來排序，不設門檻排除桌遊。

**5. 合併排序**

排序依序比較：

1. 負面分數，低的在前。
2. RRF 合併分數，高的在前。結構化分數與相似度各排一次名次，合併分數 = Σ 1/(k + 名次)，k = 60（設定值）。結構化分數同分時給同一個名次。
3. 難度，低的在前。
4. 繁中名稱。

- 沒帶 `preference_text`：只用結構化名次。沒有正面結構化偏好：只用相似度名次。兩者都沒有（玩家說「都可以」）：直接比第 3、4 項，所以「4 人、都可以」會得到最輕鬆的 3 款。
- 沒有心得摘要向量的桌遊，在相似度名次中排最後。
- 回傳前 3 款，LLM 照順序推薦。
- 沒有採用：加權相加（相似度沒有校準，權重要反覆試）；先比結構化分數、同分才比相似度（向量幾乎不會影響結果）。

**6. 心得片段檢索（embedding 用途二）**

- 在同一個「查桌遊」工具裡做：前 3 款各從自己的心得片段中取最相近的 2 段（設定值），每段帶片段 ID。
- 查詢向量：有 `preference_text` 就用它；沒有就用該款的心得摘要向量，取最有代表性的片段。
- 不另開「查心得」工具：每則訊息最多呼叫 2 次工具，放寬條件時就用完了。
- 沒有心得片段的桌遊回傳空清單。
- service 檢查 LLM 引用的片段 ID 都在這次回傳的範圍內（教材 `rag-with-citations` 的做法）。
- 繁中查詢對英文片段靠 embedding 模型的跨語言能力，由情境題組檢查效果。

**7. 向量存放（pgvector）**

| 向量 | 存在哪裡 | 欄位 |
|---|---|---|
| 心得摘要 | 桌遊資料表（暫稱 `games_advisor_games`），一款一列 | 新增可為空的心得摘要文字、心得摘要向量 `vector(EMBEDDING_DIM)`。匯入指令不寫這兩欄，由心得管線寫入 |
| 心得片段 | 新資料表（暫稱 `games_advisor_review_excerpts`），一個片段一列 | `game_id`、片段文字、片段向量。來源、語言等其他欄位由「心得來源走哪條路」與「心得怎麼變成標籤」決定 |

- 不建向量索引：資料量小，逐筆比對就夠快，結果也精確。HNSW 是近似搜尋，用 `game_id` 篩選時可能拿不到 k 筆。
- 向量長度用設定值 `EMBEDDING_DIM`。

**8. 工具參數總表**

| 參數 | 必填 | 型別 |
|---|---|---|
| `players` | 是 | 整數 1–30 |
| `max_minutes`、`min_minutes` | 否 | 整數（分鐘） |
| `youngest_age` | 否 | 整數 |
| `prefer_tags`、`avoid_tags` | 否 | 詞彙表代碼 enum 陣列 |
| `prefer_categories`、`avoid_categories` | 否 | BGG 類別 enum 陣列 |
| `prefer_mechanics`、`avoid_mechanics` | 否 | BGG 機制 enum 陣列 |
| `weight_min`、`weight_max` | 否 | 數字 1–5 |
| `preference_text` | 否 | 繁中字串 |
| `exclude_game_ids` | 否 | 桌遊 `id` enum 陣列 |
