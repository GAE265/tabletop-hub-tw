# 心得怎麼變成標籤

Type: grilling
Status: resolved
Blocked by: 03, 08, 16
Map: [桌遊推薦 Agent + 桌遊 RAG](../map.md)

## Question

決定離線批次管線：

1. 步驟：收集心得、清理、分析、彙整成每款桌遊的標籤。每一步的輸入與輸出是什麼。
2. 心得原文存不存、存在哪裡（不得進 repo）；要保留哪些追溯資訊，例如來源網址、語言、日期。
3. 一款桌遊的心得很多時怎麼處理，例如抽樣或逐段彙整。
4. 批次指令放在 `backend/` 的哪裡、怎麼執行、失敗後能不能從中斷處繼續。
5. 怎麼檢查產生的標籤合不合理。

## Answer

2026-11-08 與立倫 grilling 定案（3 輪）。

**總覽**

管線的輸入是 repo 外的 `reviews.json`（「[心得來源走哪條路](16-review-source-decision.md)」）。所有步驟都是 `games_advisor` 的後端指令，LLM 與 embedding 一律透過 `integrations/llm`、`integrations/embedding` 呼叫。執行順序：

1. 匯入桌遊（「[收錄哪些桌遊、存哪些欄位](06-game-coverage-and-fields.md)」）。
2. 產生心得摘要、產生心得片段。不依賴詞彙表，第 1 步之後隨時能跑。
3. 歸納詞彙表草稿 → 立倫審核、提交 MR → 同步詞彙表。
4. 上標籤（產生標籤草稿）→ 立倫刪除不合理的標籤 → 匯入標籤草稿。

補心得之後重跑第 2、4 步。詞彙表要不要重新歸納，見「[詞彙表改版或換 embedding 模型時怎麼處理](18-vocabulary-and-embedding-revisions.md)」。

- 沒有採用的方案：
  - 歸納詞彙表交給 Codex 做一次：綁在 Codex 的模型上，之後換地端 LLM（AGENTS.md §1、§4.2 的 `LLM_PROVIDER`）沒辦法照樣重跑；產物不能寫測試（§7）；也打破前面定下的分工：Codex 只從外部收資料、產生 repo 外的輸入檔，讀檔、分析、寫入由後端指令做。
  - LLM 工作全交給 Codex 產生 JSON，後端只匯入、轉向量：上標籤與心得摘要都不經過 `integrations/llm`，不能切換，也不能寫測試。

**1. 歸納詞彙表**

1. 擷取候選詞：每款桌遊呼叫 1 次 LLM，一次讀完該款全部心得，自由寫出候選詞。每個候選詞有 2–8 字的繁中短詞、一句描述、依據的心得 `source_url`。提示詞寫明只描述玩起來的感受，以及「[標籤詞彙表怎麼定](08-tag-vocabulary.md)」列出的 4 類不能變成標籤的內容。
2. 合併同義詞：15 款的所有候選詞（估計 150–300 個）交給 LLM 呼叫 1 次，合併成詞彙表草稿。每個標籤有代碼、繁中名稱、繁中定義；每個面向只留一個方向，反方向的候選詞捨棄並寫出原因；最多 30 個，依出現的桌遊數由多到少排序。
3. 輸出兩個檔案：
   - 詞彙表草稿：只有代碼、名稱、定義，寫到參數指定的路徑（通常就是 repo 裡的 `tag_vocabulary.json`）。檔案已存在時拒絕覆蓋，避免蓋掉審核過的版本。
   - 歸納報告：寫到 repo 外，列出每個標籤合併了哪些候選詞、出現在哪幾款、依據的 `source_url`，以及被捨棄的候選詞。含心得網址，所以不進 repo。
4. 立倫審核：參考報告直接編輯詞彙表檔案，以 MR 提交，審核結果就是 git diff。可以刪除、合併、改名稱、改寫定義、改代碼；不能新增報告裡找不到依據的標籤。新增了也不會有桌遊用到，會出現在第 3 點的提醒裡。
5. 同步詞彙表：讀 repo 裡的詞彙表檔案寫進資料表。有一項不符合就整份拒絕：
   - 代碼符合 `^[a-z][a-z0-9_]*$`，而且不重複。
   - 名稱、定義都不是空的，名稱不重複。
   - 標籤數不超過 30。這是設定值，硬性上限（「最多約 30 個」改成程式擋得住、能寫測試的上限）。

- 詞彙表正本是 repo 裡的檔案：只含立倫審核過的代碼、名稱、定義，不含心得原文；改版走 MR、留下 git 紀錄。資料庫也存一份，因為工具參數的 enum 從資料庫產生（「[條件與偏好怎麼比對桌遊](10-matching-strategy.md)」）。
- 沒有採用的方案：
  - 候選詞先轉向量分群，再由 LLM 替每群命名：分群門檻要反覆調整；embedding 已經用在排序與推薦理由出處兩處。
  - 詞彙表只寫成 Python 常數；或只存資料表、正本放 repo 外。

**2. 上標籤與信心分數**

- 每款桌遊呼叫 1 次 LLM，一次讀完該款全部心得（最多 5 篇），只能選詞彙表裡的代碼（strict schema 的 enum）。每個標籤輸出信心分數與依據的心得 `source_url`。
- 不抽樣、不逐段彙整：每款最多 5 篇，ticket 第 3 題「心得很多時怎麼處理」不需要。
- 給分標準：

  | 分數 | 標準 |
  |---|---|
  | 0.8–1.0 | 2 篇以上心得明確提到 |
  | 0.5–0.7 | 1 篇明確提到，或 2 篇以上間接提到 |
  | 0.2–0.4 | 只有 1 篇間接提到 |
  | 不輸出 | 沒有心得提到 |

  - 明確提到：直接描述這種感受，例如「大家笑到不行」。間接提到：要推論才看得出來，例如「很適合聚會」對應歡樂爆笑。
  - 有心得明確說出相反的感受時，分數降一級。
- 信心分數門檻確認為 0.5：至少 1 篇心得明確提到，才算有這個標籤。低於門檻的標籤也存進資料庫，推薦時才套用門檻，之後調整門檻不必重跑 LLM。
- 沒有採用的方案：逐篇心得各給一次分，再由程式合併（還要另訂合併規則；「標籤詞彙表怎麼定」已定由 LLM 給分）。

**3. 自動檢查（ticket 第 5 題）**

上標籤指令寫草稿前，逐款檢查：

1. 代碼都在詞彙表裡、分數在 0–1、同一款沒有重複的標籤。
2. 每個標籤至少引用 1 篇心得，引用的都是這一款的心得（`source_url` 屬於 `reviews.json` 裡這一款）。
3. 分數和引用篇數一致：0.8 以上至少引用 2 篇。

不通過就重試 1 次；仍不通過就跳過這一款，列進報告。

另外輸出提醒，不算失敗：每個標籤被幾款使用；沒有任何一款使用、或 15 款中有 12 款以上使用的標籤，標為「詞彙表可能有問題」；沒有任何標籤的桌遊。

**4. 人工驗證**

- 上標籤指令把結果寫成 repo 外的標籤草稿：每款的標籤、信心分數、依據的心得網址。
- 立倫在草稿裡刪除不合理的標籤，再由匯入指令讀回、寫進資料庫。匯入指令檢查只有刪除：草稿多出標籤或分數被改，就整份拒絕。
- 匯入時只替換草稿裡有的桌遊的標籤，搭配 `--bgg-id` 補跑時不會動到其他款。
- 重跑上標籤會產生全新草稿，不記得上次刪了哪些，要重新驗證（15 款，量不大）。
- 標籤依據的心得只存在草稿，不存進資料庫。
- 沒有採用的方案：上標籤直接寫進資料庫，事後再用指令刪（沒驗證過的標籤會先進資料庫，「只能刪」也沒有程式擋）。

**5. 心得摘要**

- 每款桌遊呼叫 1 次 LLM，讀完全部心得，寫一段 120–200 字的繁中摘要，和上標籤分開呼叫。
- 寫：氣氛、互動方式、對運氣與策略的感受、適合的場合。英文心得也寫成繁中。
- 不寫：整體好壞（好玩、無聊）；價格、版本、翻譯、購買管道；規則說明；心得沒提到的特性。
- 標籤的「不和條件、BGG 欄位重複」不適用於摘要：摘要只用來算相似度，寫到「合作」反而有助於向量比對。
- 分開呼叫的原因：摘要不依賴詞彙表，可以在立倫審核詞彙表時先跑；詞彙表改版也不用重產摘要與摘要向量。

**6. 心得片段**

- 程式依 `\n\n` 把每篇心得的 `text` 切成段落。少於 40 個中文字或 25 個英文單字的段落，併到同一篇的下一段（最後一段併到前一段）；超過 300 個中文字或 150 個英文單字的段落，在句號處切開。長度都是設定值。
- 存原文，不翻譯。繁中查詢找英文片段靠 embedding 模型的跨語言能力（「條件與偏好怎麼比對桌遊」已定）；顯示時要不要翻譯，交給「[推薦理由要寫什麼、要不要附出處](11-recommendation-reasons.md)」。
- 估計約 200 段（15 款 × 最多 5 篇 × 每篇約 3 段）。
- 不用 LLM 切：Codex 已經只擷取感受段落，程式切法可以重現、可以寫測試。

**7. 心得不足的桌遊**

- `below_minimum`（少於 2 篇，或只來自 1 個網站）照跑：只要有 1 篇，就參與歸納詞彙表、上標籤、寫摘要、切片段。心得少時分數自然偏低（第 2 點的給分標準），只有 1 篇心得產生的標籤由人工驗證把關。
- 0 篇的桌遊沒有任何輸出（已定）。
- 沒有採用的方案：只寫摘要、切片段，不上標籤；全部跳過（這幾款只能靠類別、機制、難度排序，相似度名次永遠排最後）。

**8. 指令與重跑（ticket 第 4 題）**

- 放在 `backend/app/domains/games_advisor/` 底下的一個指令模組，和匯入桌遊的指令放在一起。比照 `app/dev/seed.py`，用 `uv run python -m app.domains.games_advisor.<模組> <子指令> <檔案路徑>` 執行。
- 指令模組的角色和 `router` 相同：只解析參數、呼叫 service；service 再呼叫 repository 與 integrations（AGENTS.md §4.2）。不放 `app/dev/`：那裡只放 `AUTH_MODE=dev` 用的 seed 與開發 API。
- 子指令：匯入桌遊、歸納詞彙表草稿、同步詞彙表、上標籤（產生草稿）、匯入標籤草稿、產生心得摘要、產生心得片段。
- 每款桌遊一個交易，某款失敗不影響其他款。重跑就是覆蓋：先刪該款的舊資料再寫入，不記錄進度。`--bgg-id` 只跑指定的桌遊，「從中斷處繼續」就用它補跑失敗的那幾款。
- 要先匯入桌遊。`reviews.json` 出現資料庫沒有的 `bgg_id` 時，整個指令拒絕執行。
- 15 款、每款 1–2 次 LLM 呼叫，整個重跑的成本低，不做斷點紀錄。

**9. 資料表**

主鍵都是 UUID `id`，表名以 `games_advisor_` 開頭（AGENTS.md §4.4）。

| 資料表 | 欄位 |
|---|---|
| `games_advisor_tags`（詞彙表） | `code`（不重複）、`name`（繁中名稱）、`definition`（繁中定義） |
| `games_advisor_game_tags` | `game_id`、`tag_id`、`confidence`；同一款的同一個標籤只有一列 |
| `games_advisor_games`（新增兩欄，「條件與偏好怎麼比對桌遊」已定） | `review_summary`、`review_summary_embedding`，都可為空 |
| `games_advisor_review_excerpts` | `game_id`、`text`、`embedding`、`source_url`、`site_name`、`language` |

- 心得本身不存進資料庫（「心得來源走哪條路」已定）。
- 心得片段先不加 `title`、`author`、`published_on`：要不要顯示由「推薦理由要寫什麼、要不要附出處」決定，那時還沒有任何 migration，之後再加沒有成本。

**術語**：`GLOSSARY.md` 不變。

## Comments

- 2026-11-07 立倫：標籤是用語意分析讀心得後得到的結果，準確度可能需要人工驗證。決定管線時要包含人工驗證的步驟。
- 2026-11-07（來自「[標籤詞彙表怎麼定](08-tag-vocabulary.md)」）：詞彙表先從心得歸納再固定：LLM 自由擷取候選詞 → 合併同義詞 → 立倫審核（最多約 30 個）→ LLM 照詞彙表上標籤（enum）。每個標籤有英文代碼、繁中名稱、一句繁中定義；有 4 類內容不能變成標籤（見該 ticket）。這張要決定：歸納與審核的步驟、信心分數（0–1，由 LLM 給）的給分標準、逐則心得還是整款桌遊給分、人工驗證刪除標籤的流程（只能刪，不能新增或改分數）、詞彙表定案後存在哪裡。
- 2026-11-07（來自「[條件與偏好怎麼比對桌遊](10-matching-strategy.md)」）：管線除了標籤，還要產出兩種 embedding 的資料：(1) 每款桌遊一段繁中心得摘要（描述玩起來的感受）與摘要向量，寫進桌遊資料表新增的兩個欄位；(2) 從心得切出心得片段，每段轉成向量，存進新的心得片段資料表（`game_id`、片段文字、片段向量）。這張要決定摘要的長度與產生方式、片段怎麼切、片段存原文還是翻譯，以及片段資料表的其他欄位。信心分數門檻暫定 0.5（低於門檻當作沒有這個標籤），定好給分標準後回頭確認。
- 2026-11-08（來自「[心得來源走哪條路](16-review-source-decision.md)」）：心得由 Codex 用網路搜尋收集，輸出 repo 外的 `reviews.json`（格式見 [collect-reviews.md](../prompts/collect-reviews.md)），管線的輸入就是這個檔案，不用再設計收集步驟。每款最多 5 篇、至少 2 篇，`text` 已是逐字擷取的感受段落，可能是繁中或英文。心得不存進資料庫；心得片段資料表從所屬心得複製 `source_url`、`site_name`、`language`。這張還要決定：`below_minimum` 的桌遊（少於 2 篇或只有 1 個網站）照跑還是跳過；每款只有 5 篇時，第 3 題的「心得很多時怎麼處理」可能不需要。
- 2026-11-08 grilling 進行中（第 1 輪）：上標籤是每款呼叫 1 次 LLM、一次讀完全部心得，每個標籤附依據的心得（不抽樣、不逐段彙整）；詞彙表正本是 repo 裡的檔案，由指令同步進資料表；人工驗證用 repo 外的草稿檔，讀回時程式檢查只有刪除；心得摘要每款 1 次、120–200 字繁中，和上標籤分開呼叫；心得片段由程式依段落切、存原文；`below_minimum` 照跑。待定：哪些步驟寫成後端指令（立倫要求依專案規範重擬選項）。
- 2026-11-08 grilling 進行中（第 2 輪）：歸納詞彙表、上標籤、心得摘要、心得片段都寫成後端指令（依 §4.2、§7 與「Codex 只收資料」的分工）；給分標準四級、門檻 0.5、低於門檻也存；上標籤三項自動檢查（不通過重試 1 次再跳過）與詞彙表提醒；指令放 `games_advisor` 的指令模組，每款一個交易、重跑即覆蓋、`--bgg-id` 補跑；資料表 `games_advisor_tags`、`games_advisor_game_tags`、`games_advisor_review_excerpts`。待定：歸納詞彙表的步驟與審核流程。
