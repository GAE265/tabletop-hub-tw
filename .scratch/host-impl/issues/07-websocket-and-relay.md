# 07：WebSocket 與轉送（聲音、計時、重連、重送、接話方式）

## 要做什麼

新檔案 `backend/app/domains/host/relay.py`（非同步），加上 `router.py` 的 WebSocket 入口。它把裝置、語音模型、圖三邊接起來。全程用 `FakeRealtimeVoiceProvider` 測，不連阿里雲。

這張是十張裡最大的一張（38 行情境）。一個對話做不完時，照下面的順序分段，每段各自先寫測試：

1. **連線**（spec §12.1）：核對通行碼後才開語音模型的連線；連上先送 `state`；第二支裝置連上時取代第一支；裝置斷線就關掉語音模型的連線、這場主持保留；已結束的主持連上後變回 `active`。五個錯誤碼（spec §12.4）。
2. **聲音與訊息**（spec §12.2 到 §12.4）：兩個方向的 PCM 原樣轉送；裝置送的四種 JSON、後端送的五種 JSON；`utterance` 的開始與結束；`flush`。
3. **跑圖並執行結果**：按鍵、辨識文字、工具請求、播完回報都排隊交給圖（圖是同步的，用另一條執行緒跑），再照圖交回的清單去做：請主持人開口、送 `flush`、送新的 `state`、回工具結果。
4. **語音指令的兩條路**（spec §5.2）：片段辨識文字等 0.3 秒沒有新片段才執行；模型呼叫工具時用後端自己的辨識文字核對，沒過就告訴模型這不是指令；同一句話只執行一次（用那句話的編號）。
5. **接話方式與聲線**（spec §7）：開連線時把接話方式、聲線代號、歷史 50 輪、靈敏度 0.5 交給整合層；按住說話的按下（取消回答並 `flush`）與放開（請模型回答）；切換接話方式後重新連線接著走。
6. **重新連線時交回的內容**（spec §9）：完整指令加現況，主持人只說 `back_to`；暫停中連回來不說。
7. **計時**（都用假時鐘測）：轉交思考模型第 8 秒補 `wait_longer` 一次、第 15 秒或錯誤就放棄並交出片段與 `not_sure`、晚到的答案丟掉（spec §8.3）；每 150 秒送不出聲的系統訊息帶現況，主持人剛說過話就重算（spec §10.1）。
8. **重連與重送**：和語音模型斷線後重試 3 次，間隔 1、2、4 秒（spec §10.2）；請主持人開口被拒就每 0.5 秒重送，直到送出、換了節點、或進入主持暫停，`wait_longer` 不重送（spec §10.3）。
9. 每一輪的用量記進紀錄；紀錄不寫玩家說的話與金鑰（spec §13.5）。

- 2026-11-22：spec 沒寫明、這張先定的做法：
  1. 模型呼叫指令工具時，後端還沒收到那句話的辨識文字：先回「會用辨識文字核對」，等辨識文字到了走後端自己看的那條路。只有片段時直接用片段核對，不等 0.3 秒。
  2. 那句話的編號帶不出來時（工具請求沒有編號）：用最近一句的辨識文字核對，同一個動作 3 秒內只執行一次。這是 spec §5.2 寫的退路，阿里雲帶不帶得出編號在「08：阿里雲的 cloud 實作與外部服務測試」確認。
  3. 等思考模型時，主持人自己開口回了別的話（不是後端要它說的）：當成玩家說了「不是閒聊也不是指令」的話，舊題作廢（spec §8.4）。
  4. 主持暫停中「接著主持」：主持人說接回流程那一句（照 M-06）；後端自己重連語音模型時，暫停中不說（照 spec §10.2）。
  5. 舊題作廢時，舊的工具請求回一則「已作廢，不用回答」把它收掉。
  6. 即時語音的實作在第一次有裝置連上時才建立（`router.py`），沒有動 `main.py`。
