# Design

## Context

- 規格：根目錄 `影片生產器規格.md` 的產品流程 1–6。1d 的原始範圍（見已歸檔的 `add-rules-video-maker` proposal）：API、資料表、前端精靈、發布、OCR 或從 `rules_ingest` 讀規則書、部署設定。
- 引擎（命令列）都以「資料夾」運作：`video.json`、`assets/`、`cache/`（段影片、旁白）、`out/`、`revisions/`。
- 已有、可沿用：
  - `rules_ingest`（瑋鋐）：照片 → Vision OCR → `games_manual` 每頁 Markdown；`shop_staff`、`admin` 可用；有前端頁面。
  - `integrations/storage`：`put`／`get`／`delete`，有本機（`STORAGE_LOCAL_DIR`）與雲端兩種實作。
  - 前端：`core/platform/image_picker.dart`（file_picker，手機上可以選相機）、`lesson_video_player.dart`（只支援 YouTube）。
- **沒有**：背景工作的機制、進度回報、手機上標區域的方式。

## Goals / Non-Goals

**Goals**：檢查點前，店員只用手機完成「上傳規則書 → 草稿 → 拍素材、標區域 → 產生 → 看」；長時間工作離開頁面再回來仍看得到進度與結果；失敗時說得出原因與下一步。

**Non-Goals**：見 proposal「這階段不做」與「檢查點之後再決定」。

## Decisions（2026-11-21 永傑確認 Q1–Q8）

**D1 影片專案（`rules_qa_video_projects`）。** 一個專案＝一章（Q4）。
- MR 1 的欄位：`id`（UUID）、`game_id`、`shop_id`、`created_by`、`chapter_number`（≥ 1）、`chapter_title`（1–50 字，去掉前後空白後不可為空）、`created_at`、`updated_at`。
- 本章頁、參考頁、段資料等欄位**等 MR 4、MR 5 用到時再加**（2026-11-21 永傑決定：沒有寫入也沒有測試的欄位，審核看不出設計對不對；段資料欄位會決定資料庫與 `video.json` 誰是正本，要在 MR 4 一起決定）。
- **`step`（目前步驟）不存欄位，由其他狀態推出**。MR 1 沒有其他狀態，固定回 `pages`（上傳規則書）；之後的 MR 依草稿、素材、工作的狀態推出 `draft`、`assets`、`render` 等值，加值時在該 MR 寫明推導規則。
- 建立：店員的店家用登入身分的 `shop_id`，body 帶別家店回 403；管理員必須帶 `shop_id`（沒帶 422，店家不存在 404）。
- **同一間店、同一款遊戲、同一章可以建立多個專案**（2026-11-21 永傑決定）：例如重拍一版或比較兩份草稿，不加唯一限制。
- 列表：`page`（≥ 1）、`page_size`（1–100，預設 20），依 `updated_at` 由新到舊；回 `{items, total}`。
- 權限：`shop_staff` 只能存取自己店的專案（別家店的回 404，不透露存在）；`admin` 全部；`player` 403；沒登入 401。

**D2 非同步工作（`rules_qa_video_jobs`，MR 2；2026-11-21 永傑確認）。** 草稿（含涵蓋檢查）、產生影片、修改一律做成工作（Q7）：
- **kind**：`draft`（產生草稿）、`render`（產生影片）、`revise`（用一句話修改）。處理函式分別在 MR 5、MR 9、MR 11 接上；MR 2 只做機制，用測試裡的假處理函式驗證。
- **狀態**：`queued`（等待）→ `running`（處理中）→ `succeeded`（完成，結果在 `result`）或 `failed`（失敗，原因在 `error`）。`succeeded`、`failed` 不再改變；重試＝建立新工作。
- **欄位**：`id`、`project_id`、`kind`、`status`、`progress`（0–1）、`message`（現在在做什麼）、`error`（給店員看）、`error_detail`（給開發者看：例外類型與訊息，最多 2000 字，不在 API 回傳）、`result`（JSONB）、`created_by`、`created_at`、`started_at`、`finished_at`。
- **同時兩個工作回 409**：部分唯一索引保證同一個專案 `queued`／`running` 最多一筆；寫入違反時回 409 `RULES_VIDEO_JOB_RUNNING`，`details` 附進行中的工作 id。由資料庫保證，兩個請求同時送進來也只有一個成功。
- **卡死的工作的出口**：建立新工作時，同專案 `running` 且 `started_at` 超過 **30 分鐘**的工作先標為 `failed`（「工作逾時，已中止」），再建立新的。未超時的仍回 409。逾時中止後，原本的執行緒若之後才做完，也不會改寫它的狀態（結束與回報進度都只更新 `running` 的工作）。
- **處理函式必須設逾時**：MR 5、MR 9、MR 11 的處理函式呼叫 LLM、TTS、ffmpeg 時都必須設逾時（LLM 用 `LLM_TIMEOUT_SECONDS`；ffmpeg 子程序要加上限），不能依賴 30 分鐘的出口。
- **背景執行緒**：後端啟動時開一個執行緒（FastAPI lifespan），關閉時停止；`RULES_VIDEO_WORKER=false` 不啟動。每次取一個最早的 `queued` 工作（`FOR UPDATE SKIP LOCKED`），同時改成 `running`。建立工作時通知執行緒立刻取，平常每 2 秒檢查一次。處理函式用 `report(進度, 說明)` 回報，每次用獨立的短交易寫入。
- **伺服器重新啟動**：啟動時、執行緒開始前，把 `running` 的工作標為 `failed`（「伺服器重新啟動，工作中斷，請重新開始」）；`queued` 保留繼續做。**已知限制**：假設後端只有一個程序。
- **例外的記錄**：處理函式拋出例外時，(1) 伺服器 log 用 `logger.exception` 記下工作 id、kind 與堆疊；(2) `error`：拋出 `JobFailed("…")` 用那句話，其他例外用「發生未預期的錯誤，請重試；若持續發生請通知管理員」；(3) `error_detail`：例外類型與訊息。寫入失敗結果時本身又出錯，只記 log，執行緒繼續；那個工作停在 `running`，30 分鐘後由上面的出口釋放。沒有對應 kind 的處理函式：`failed`（「這種工作還沒有實作」）。
- **API**：`GET /rules-videos/{id}/jobs`（新的在前、分頁）、`GET /rules-videos/{id}/jobs/{job_id}`；權限同專案。建立工作的 API 在 MR 5、MR 9、MR 11（建立時回 202）。

**D3 規則書頁面。** 沿用 `rules_ingest` 的上傳與 OCR，不另做。草稿工作從 `games_manual` 讀店員選的本章頁與參考頁（`read_manual_pages`）。`games_manual` 沒有語言欄位，頁面的 `lang` 一律記為 `zh`（之後需要再加設定）。

**D4 用語對照表（`rules_qa_video_terms`，MR 3；2026-11-21 永傑確認）。** 每款遊戲一份、所有店家共用（Q5 b）：`game_id`（主鍵）、`terms`（JSONB，格式同 `terms.json`）、`updated_by`、`updated_at`。
- `PUT /api/v1/games/{game_id}/video-terms`：只有 `admin`；body `{"terms": [...]}`，整份取代。`GET` 同路徑：`admin`、`shop_staff` 可看。
- **每一筆**：`en`、`zh` 必填，去掉前後空白後 1–100 字；`key` 選填（1–100 字）；`avoid` 選填，字串陣列（每個 1–100 字；空字串會比對到所有文字，所以不允許）；`category` 選填，`generic`（泛稱）或 `single`（單一種牌）。最多 500 筆。
- **`en` 不能重複**：去掉前後空白、不分大小寫後比對（「White Rose」與「 white rose 」算重複）→ 422 `RULES_VIDEO_TERMS_DUPLICATE`。
- **`key` 可以重複**：規則書常用兩個英文名稱指同一個區域或物件，例如 *White Rose placement area* 與 *Sanctuary* 都對到 `white_rose_zone`（《血與刃》的對照表就是這樣）。`key` 的用途是把用詞對到素材或區域，本來就可能多對一。但**同一個 `key` 的 `category` 必須一致**：只有兩筆都填了 `category` 才比較，一筆有、一筆沒有不算不一致；`key` 也是去掉空白、不分大小寫後比對。不一致 → 422 `RULES_VIDEO_TERMS_CATEGORY_CONFLICT`。
- **驗證規則與命令列共用**：`load_terms`（讀本機 `terms.json`）與 API 用同一份規則，命令列遇到上述錯誤也會報錯。
- **還沒上傳時 `GET` 回 404 `RULES_VIDEO_TERMS_NOT_FOUND`**，不回空表：「從未上傳」與「上傳了空表」意思不同——上傳空表是管理員確認這款遊戲不使用對照表；從未上傳是還沒準備好。草稿頁要能分辨，才知道該不該提醒店員。
- 草稿工作（MR 5）有對照表就帶入，沒有就不帶；**MR 6 的草稿頁在「從未上傳」時提示店員「這款遊戲還沒有用語對照表，草稿的用詞品質可能下降」**。

**D11 規則書文字與草稿（MR 4 頁面文字、MR 5 草稿工作；2026-11-21 永傑確認，原「MR 4 草稿 API」拆成兩個）。**

*段資料的正本：資料庫（永傑確認）。* 兩個選項的後果：

| | A：資料庫為正本（採用） | B：工作資料夾的 `video.json` 為正本 |
|---|---|---|
| 伺服器重啟、重新部署 | 不受影響 | 雲端（Container Apps）的磁碟會被清掉，店員的草稿與修改紀錄跟著消失；本機驗收環境不會清，但換機器就沒了 |
| 備份 | 跟著資料庫備份 | 要另外備份資料夾 |
| 與工作的一致性 | 草稿寫入與工作狀態在同一個資料庫，可以用交易保證「失敗時原本的草稿不變」 | 檔案與資料庫各自寫入，中途失敗會不一致 |
| 同時被改 | 用版本號（`video_version`）偵測：工作開始後專案被改過就不覆寫 | 要自己做檔案鎖 |
| API 讀取 | 直接查資料庫 | 每次讀檔案；多台伺服器時讀不到 |
| 輸出影片 | 每次先把段資料寫成工作資料夾的 `video.json`、照片放進 `assets/`（成本很低，段資料只有幾十 KB） | 直接用 |
| 命令列工具 | 要另做「匯出成資料夾」的指令才能用 `stills`、`compare` 除錯（之後再做） | 直接用 |

理由：決定性的是**交易一致性**（失敗時原本的草稿不變）與**版本偵測**（拍照上傳、修改與草稿工作可能同時發生），這兩點只有資料庫做得乾淨。「重啟會清掉磁碟」只在雲端成立，驗收用的電腦不會清。代價是輸出前要「展開」成資料夾，以及命令列除錯要多一個匯出指令。
- 正本的範圍：段資料（含每段的 `state`、`revisions`）、素材的中繼資料（照片檔名、方向、區域座標）、**店員編輯過的規則書文字**（見下）。照片本身是檔案，不放資料庫。

*存放介面與工作資料夾（D5 的細節）：*

| 東西 | 放哪裡 | 遺失的後果 | 哪個 MR |
|---|---|---|---|
| 店員編輯過的規則書文字（本章頁、參考頁） | 資料庫（`page_texts`） | 店員要重新編輯 | MR 4 |
| 段資料、修改紀錄、素材中繼資料 | 資料庫（`video`） | 不可遺失 | MR 5 |
| 涵蓋檢查結果 | 資料庫（`coverage`） | 重跑一次涵蓋檢查（一次 LLM） | MR 5 |
| 素材照片原圖 | 存放介面：`rules_videos/<專案>/assets/<檔名>` | 店員要重拍 | MR 7 |
| 成品影片 | 存放介面：`rules_videos/<專案>/renders/<工作>.mp4` | 重新產生 | MR 9 |
| 展開的 `video.json`、`assets/` 副本 | 工作資料夾 `RULES_VIDEO_WORK_DIR/<專案>/` | 自動重建 | MR 9 |
| 段影片、旁白快取 | 工作資料夾的 `cache/` | 段影片全部重新編碼；**旁白要重新呼叫 TTS（花錢）**——之後可以考慮把旁白快取移到存放介面 | MR 9 |

- **重新產生草稿時沿用照片與區域**在 MR 7：照片在 MR 7 才有，而且草稿模式仍要求有寫檔名的照片檔存在，要先從存放介面放回工作資料夾。MR 5 的重新產生是「整份取代」。

*為什麼要讓店員先編輯規則書文字（2026-11-21 中文規則書小實驗）：*
- **OCR 錯字會直接帶進草稿**：第 7 頁「**蓋住的**」被辨識成「**有蓋牌的**」，三次草稿的字幕都照抄；草稿與涵蓋檢查都以辨識出的文字為準，看不出錯字。
- **章節不等於頁面**：某款遊戲的一個章節在第 7 頁，第 8 頁只有最後一段屬於本章。整頁帶入會多出不屬於本章的規則，連帶多列用不到的立體素材。
- 第三輪（第 7 頁修正錯字＋第 8 頁只留最後一段）永傑判定合格：規則錯誤 0 次、素材與細節 1 次。**注意：這是工程師模擬店員編輯後的文字得到的結果，真正的驗證是手機實測（tasks 3.1）。**
- 三次的第一份輸出都有「翻牌沒有牌背」，都由改寫修好：**改寫一次是流程的關鍵一環**，不是可有可無的保險。
- 編輯後的文字存在**專案上**，不改 `games_manual`：`games_manual` 是整本規則書，規則問答也在用；同一頁可能分給兩章，各章要刪的段落不同。

**MR 4 頁面文字（migration 0019，加在 `rules_qa_video_projects`）**

| 欄位 | 說明 |
|---|---|
| `chapter_pages` | int[]，預設 `{}`：本章用哪幾頁（`games_manual` 的頁碼） |
| `reference_pages` | int[]，預設 `{}`：參考頁（只查牌名與分類，不可寫成旁白） |
| `page_texts` | JSONB，預設 `{}`：`{"頁碼": {"text": 編輯後的文字, "original_hash": 開始編輯時原文的雜湊}}`；本章頁與參考頁都有 |

| `pages_version` | int，預設 0：頁面文字每存一次加 1（2026-11-21 永傑確認；MR 5 的 `draft_pages_version` 與它比對，判斷草稿是不是依舊文字產生） |
- `GET /rules-videos/{id}/pages` → 可選的頁（`games_manual` 有哪些頁）、目前的本章頁與參考頁，以及每頁：原文（`games_manual` 目前的內容）、編輯後的文字、**刪掉的段落**、**改過的行**、`original_changed`（開始編輯後原文被重新上傳過）、`pages_version`。還沒選過頁時，每頁的編輯後文字預設等於原文。
- `PUT /rules-videos/{id}/pages`，body `{"chapter_pages": [7, 8], "reference_pages": [2], "texts": {"7": "…", "8": "…"}}` → 200，回傳同 GET。整份取代；沒給文字的頁用原文。
  - 頁碼：本章至少 1 頁、最多 20 頁；每頁 ≥ 1；不能重複；本章頁與參考頁不能重疊；都必須已經上傳到 `rules_ingest`（缺的回 422 `RULES_VIDEO_PAGES_MISSING`，列出缺哪幾頁）。
  - 文字：每頁最多 10000 字；`texts` 只能有選了的頁（多的回 422）；本章頁編輯後全部是空白回 422（沒有東西可以產生草稿）。
- **刪掉的段落與改過的行**：以行為單位比對原文與編輯後的文字（去掉前後空白、略過空行），用 `difflib.SequenceMatcher` 對齊。原文的一行在編輯後**完全相同** → 不列；**相似度 ≥ 0.6**（`SequenceMatcher.ratio()`）→「改過」（例如錯字修正：「把所有有蓋子的木箱排成一列」→「把所有蓋好的木箱排成一列」整行相似度約 0.88）；**相似度 < 0.6 或找不到對應** →「刪掉」，連續刪掉的行合成一段。門檻 0.6 寫成常數並有測試（剛好 0.6 算改過、低於算刪掉）。
- 每一處差異都附**原文與編輯後的文字**（刪掉的只有原文），**MR 6 的畫面對每一處同時顯示原文與編輯後**，不只顯示「刪掉」「改過」的分類結果（2026-11-21 永傑決定），讓店員自己確認。
- 權限同專案（別家店 404、玩家 403、沒登入 401）。
- 專案的 `step` 不變（MR 4 還沒有草稿，仍是 `pages`）。

**MR 5 草稿工作（migration 0020）**

| 欄位 | 說明 |
|---|---|
| `video` | JSONB，可為空：段資料正本；空值代表還沒有草稿 |
| `video_version` | int，預設 0：段資料每改一次加 1；工作開始時記下，寫入前比對，不同就不覆寫 |
| `coverage` | JSONB，可為空：最近一次涵蓋檢查（`done`＋結果，或 `not_done`＋原因）；空值代表還沒檢查 |
| `coverage_version` | int，可為空：涵蓋檢查是對哪一個 `video_version` 做的；與 `video_version` 不同就是過期 |
| `draft_pages_version` | int，可為空：草稿用的是哪一版頁面文字；與 `pages_version` 不同時，草稿標示「依舊文字產生」 |

- `POST /rules-videos/{id}/jobs`，body `{"kind": "draft"}` → 202，回工作（MR 9、MR 11 用同一個端點，`kind` 不同）。還沒存過頁面文字回 422 `RULES_VIDEO_PAGES_NOT_SET`。
- `GET /rules-videos/{id}/draft` → 每段的句子（旁白、字幕、出處頁）、素材清單（必拍／選拍、拍攝說明、代表牌、區域名稱、是否已有照片）、涵蓋檢查摘要（`done`／`not_done`／`stale`）、用語對照表狀態（`used`／`empty`／`missing`；`missing` 時附上提示「這款遊戲還沒有用語對照表，草稿的用詞品質可能下降」）、**`pages_stale`**（頁面文字在草稿產生後被改過時為 true，並附「這份草稿依舊的頁面文字產生，建議重新產生」）、`video_version`。還沒有草稿回 404 `RULES_VIDEO_DRAFT_NOT_FOUND`。
- 專案的 `step`：`video` 為空 → `pages`；有草稿 → `draft`（MR 7、MR 9 再細分）。

*草稿工作的處理函式（`kind = draft`）：*
1. 讀專案，記下 `video_version` 與 `pages_version`；**讀店員編輯過的文字**（`page_texts`，不讀 `games_manual`）；頁面的 `lang` 記為 `zh`。
2. 讀用語對照表：有就帶入；空表不帶；從未上傳不帶，結果記 `missing`。
3. `generate_script`（照 1c 的規則：自動清理 C1–C4、檢查、改寫一次）。
4. 涵蓋檢查（`check_coverage`，**只用編輯後的本章頁文字**）：失敗或回空清單時，草稿照樣存，`coverage` 記 `not_done` 與原因。
5. **一個交易**寫入 `video`、`video_version + 1`、`coverage`、`coverage_version`、`draft_pages_version`，條件是 `video_version` 還是第 1 步記下的值；不是就工作失敗（「產生草稿期間專案被修改，請重新產生」），不覆寫。
6. 工作的 `result`：段數、句數、素材數、待拍數、自動清理紀錄、涵蓋檢查是否完成、對照表狀態。
- **任何一步失敗，段資料都不變**：寫入只發生在第 5 步，而且是單一交易。

*LLM 的逾時、重試與店員說明（沿用 MR 2：處理函式必須自己設逾時）：*
- 每次呼叫：`LLM_TIMEOUT_SECONDS`（維持 30 秒，永傑決定）＋ OpenAI SDK 內建的 2 次重試（連線錯誤、逾時、429、5xx）。草稿最多 3 次呼叫（產生、改寫、涵蓋檢查），最壞約 3 ×（3 × 30 秒）＝ 4.5 分鐘，在 30 分鐘的工作逾時之內。
- 店員看到的說明：

  | 情況 | `error`（給店員） |
  |---|---|
  | LLM 連不上、逾時、忙碌（`LLMUnavailable`） | AI 服務暫時無法使用（連線逾時或忙碌），請稍後再產生一次 |
  | LLM 拒絕或沒完成輸出（`LLMOutputRejected`） | AI 沒有完成草稿，請再產生一次；若持續發生請通知管理員 |
  | 改寫一次仍不通過（`ScriptRejected`） | AI 產生的草稿沒有通過檢查（列出前 3 個原因）。可以再產生一次；若一直失敗，請檢查規則書頁面的文字 |
  | 工作期間專案被改 | 產生草稿期間專案被修改，請重新產生 |
- 與命令列的差異：命令列會把兩次不通過的原始輸出存成 `rejected-1.json`、`rejected-2.json`；MR 5 不保留（`error_detail` 只記錯誤清單）。

*已知限制（MR 4、MR 5）：*
- **OCR 錯字會直接帶進草稿**：只能靠店員在產生草稿前修正文字（MR 6），以及檢查字幕。
- **每份草稿多約 15 秒改寫**：第三輪實驗三次都因結構錯誤（翻牌沒有牌背、目標用中文區域名稱、指向不存在的槽位）改寫一次。提示不調整（永傑決定）。
- **逾時餘裕約 1.5 倍**：實驗中最長一次呼叫 19.5 秒，逾時 30 秒；章節變長再處理。
- **這一版不能輸出繪製的立體素材**（`drawn`，例如骰子、白水晶）：《血與刃》步驟三不受影響（只有平面素材）；其他需要較多素材的遊戲，草稿會列出繪製素材，到產生影片那一步（MR 9）會被擋下。
- **涵蓋檢查看不到用語對照表**：對照表把規則書用詞改成影片用詞時（例如「花朵卡片」→「白薔薇」），涵蓋檢查可能誤報。不改涵蓋檢查（永傑決定）。

**MR 6～10 的規劃（2026-11-21 永傑確認）。** 決定：(1) 涵蓋檢查「過期」改用旁白與字幕的雜湊判斷，先在 MR 5 修；(2) 照片與影片用帶身分的 API 下載、轉暫存網址；(3)「匯入」這一版不開放給店員；(4)「已檢查」只存在畫面上；(5) 照片只收 JPEG、PNG，上限 15 MB；(6) 外觀：永傑先決定 4 個關鍵畫面（草稿確認、素材拍照加拖框、產生進度、播放），其餘用 App 現有元件。 每個 MR 一節：設計、情境表格、待決問題。手機頁（MR 6、8、10）由永傑負責外觀，最後一節列出「需要永傑決定外觀」的畫面清單。

**D13 MR 7 素材 API（`feature/rules_qa-video-assets-api`）**

*範圍*：存放介面接上後端、素材照片上傳與讀取、方向、區域座標、缺什麼的檢查、重新產生草稿時沿用照片與區域。

- **存放介面**：`main.py` 建立 `app.state.storage`（`integrations/storage` 的工廠，本機用 `STORAGE_LOCAL_DIR`；@立倫）。素材照片的 key：`rules_videos/<專案>/assets/<asset_key>-<短 id>.<副檔名>`；換照片時刪掉舊檔。
- **上傳**：`PUT /rules-videos/{id}/assets/{asset_key}/photo`（multipart）。
  - 只接受 JPEG、PNG（用 Pillow 開得起來才算；HEIC 見待決 3）；大小上限見待決 3。
  - **依 EXIF 轉正**後再存（手機照片常帶方向資訊），區域座標都以轉正後的圖為準。
  - 寫入段資料的 `assets[].file`；`video_version` 加 1、更新 `updated_at`（Q1 的「最後一次動作」）。
- **讀照片**：`GET /rules-videos/{id}/assets/{asset_key}/photo` 回傳圖檔（帶身分，權限同專案）；讀取方式見待決 1。
- **方向與區域**：`PATCH /rules-videos/{id}/assets/{asset_key}`，body `{"orientation": 0|90|180|270, "regions": {"white_rose_zone": [x, y, w, h], …}}`。座標是相對比例：0 ≤ x、y；w、h > 0；x + w ≤ 1、y + h ≤ 1；區域名稱必須是草稿列的那些。`video_version` 加 1。
- **缺什麼**：`GET /rules-videos/{id}/readiness` → 必拍但沒有照片的素材、沒有座標的區域、本版不支援的繪製素材（`drawn`）。MR 9 產生影片前也用同一份檢查。
- **重新產生草稿時沿用**：草稿工作開始時，把舊段資料裡同一個 `asset_key` 的照片、方向、區域帶到新草稿；新草稿沒有的素材，照片留在存放介面不刪（之後重新產生可能又用到；Q1 的刪除時一起清）。草稿模式要求照片檔存在，所以檢查前先從存放介面放回工作的暫存資料夾。
- **涵蓋檢查過期的判斷要改（見待決 2）**。

*實作決定（2026-11-21，做 MR 7 時補充）*：
- **存放介面**：遠端分支沒有人在接（2026-11-21 確認），由本 MR 在 `main.py` 建立 `app.state.storage`（永傑同意，@立倫）。草稿工作的處理函式不需要存放介面（見下一點），所以 `main.py` 只多建立存放介面。
- **沿用照片的時機**：在涵蓋檢查之後、寫入之前，把舊段資料同一個 `asset_key` 的 `file`、`orientation`、還在新草稿裡的區域座標帶到新草稿。涵蓋檢查不需要照片，所以不必先把照片放回暫存資料夾（原規劃的「檢查前先放回」省略）。
- **改方向會清掉區域**：區域座標是以「套用方向之後」的圖為準；`orientation` 改變而 body 沒有同時給 `regions` 時，所有區域改回待量測（`null`），回應會帶出來，手機頁提示重新標。換照片時方向改回 0、區域座標保留（同一張牌的版面通常相同），由手機頁提示重新確認。
- **素材明細**：加 `GET /rules-videos/{id}/assets/{asset_key}`（方向、區域座標、有沒有照片），給 MR 8 的單一素材頁與標區域頁用。
- **缺什麼**：第 1 階段的段資料規定每個照片素材都要有檔案才能輸出，所以**選拍的素材沒有照片也會擋住產生影片**，readiness 會列出並標「選拍」。之後若要允許略過選拍素材，要在 MR 9 處理（引用它的段要改掉），先記為已知限制。
- 大小上限 15 MB 寫在 domain 常數，不加設定（不改 `core/config.py`）。

*待決問題*：
1. **手機怎麼讀照片與影片（決定）**：照片與影片都用帶身分的 API 下載（前端用 dio 取得內容，照片用 `Image.memory`，影片轉成瀏覽器的 blob 網址交給播放器），不做簽名網址。**已知限制**：只能在網頁使用；影片要整支下載完才能播；上雲端後改成有時效的簽名網址。

  4. 成品存到存放介面 `rules_videos/<專案>/renders/<工作 id>.mp4`；結果記總長、哪些段重新編碼、哪些沿用。
  5. 修改過的段狀態改為 `rendered`（沿用第 2 階段的 `mark_rendered`）；`updated_at` 更新。
- **逾時**（MR 2 的規定）：ffmpeg 子程序加上限（`integrations/video` 的 `Ffmpeg.run`、`popen` 加 `timeout`，預設依影片長度估）；TTS 每句加逾時；都要在 30 分鐘的工作逾時之內。
- **API**：`POST .../jobs` 開放 `{"kind": "render"}`（缺東西回 422 `RULES_VIDEO_NOT_READY`，附缺的清單）；`GET /rules-videos/{id}/render` → 最近一次成功的成品（下載路徑、總長、重新編碼與沿用的段、產生時間）；`GET /rules-videos/{id}/render/video` → 影片檔（權限同專案，見 MR 7 待決 1）。
- 專案的 `step`：有草稿、素材還沒齊 → `assets`；齊了、還沒有成品 → `render`；有成品 → `done`（推導規則寫進 design）。

**D17 整個遊戲一支影片（2026-11-22 永傑決定；後端 `feature/rules_qa-video-whole-game-api`、前端 `feature/rules_qa-video-whole-game-page`）**

*流程*：店員選遊戲（規則書由管理員預先匯入）→ 自動開始產生草稿 → 素材（拍照、標區域）→ 產生影片 → 觀看。建立表單只剩「選遊戲」；影片標題自動用「〈遊戲〉 規則教學」。「頁面文字」那一步從店員流程移除（OCR 錯字由管理員匯入時處理，店員靠之後的修改補救）。草稿畫面保留，只顯示進度與結果摘要，不擋流程。

*範圍*：只講「開局（setup）、走完一輪（round）、獲勝方式（win）」三格。
- **分類呼叫**（`video_scope.py`）：輸入整本規則書，輸出三格與排除清單（附原因）。每筆都引用原文片段；程式忽略空白差異後檢查片段確實出現在那一頁，對不上的不採用（記在 `dropped`）。某一格是空的就讓草稿工作失敗：「規則書裡找不到「〈格〉」的內容…」。
- **產生**：一次呼叫，輸入三格的原文片段（不是整本），段資料用三個 chapter（`setup`、`round`、`win`），每段標 `chapter`，程式依三格排序。實測有「整條沒講」的規則時，再評估改成每格各一次呼叫並共用素材清單（這次不做）。
- **提示與檢查**：素材 kind 只能是 `flat_photo`（schema 只允許它，檢查也會擋 `drawn` 並進自動改寫）；區域名稱只能用素材列出的名稱；教學內容不用「次」（「一次機會」改說「一個機會」）；輔助說明的素材標選拍；泛稱牌用代表牌；不設硬性素材數上限。素材加 `label`（給店員看的中文名稱），integrations/video 的素材也接受這個選填欄位。
- **涵蓋檢查**：三格各做一次（只拿這一格的片段比對這一格的段，排除的內容不檢查），維持提示、不擋下；摘要依格顯示（`coverage.slots`），合計把三格加起來（rule_id 前面加格的 key）。

*欄位與 migration 0020*（@瑋鋐）：
- `chapter_number`、`chapter_title` 改為可空；空值＝整個遊戲一支影片。API 兩個一起給＝舊的單章模式（命令列與既有資料），都不給＝整個遊戲，只給一個回 422。
- `chapter_pages` 保留，意思改成「這支影片用到的頁」，建立時預設全選規則書的頁；`reference_pages` 不再使用（一律空陣列）。
- **分類結果放新的 JSONB 欄位 `classification`**（含排除清單），不放進現有欄位。理由：`coverage` 每次涵蓋檢查都整份取代、也依旁白雜湊判斷過期，生命週期和分類不同；`video` 是 video.json 的正本，欄位受段資料格式檢查；分類結果之後的「新增一段」（MR 11、12）要用排除清單找漏講的內容，放獨立欄位才不會被其他步驟覆寫。
- 店員看得到的 API 都不回傳分類結果與排除清單。

*錯誤訊息*：店員看到的錯誤不出現段代號、highlight key 這類內部代號，細節放 `error_detail`（`JobFailed.detail`，API 不回傳）；拿掉「請檢查規則書頁面文字」。素材頁的錯誤用素材名稱（`label`，舊草稿沒有時用 reason）指出是哪一個素材。

*重新產生草稿*：照片、方向、區域照舊依 `asset_key` 與區域名稱沿用（MR 7）。新草稿的 `asset_key` 或區域名稱和舊的不同時，那個素材就要重拍或重標（舊照片留在存放空間，不刪）。用語對照表有 key 的素材，`asset_key` 固定用對照表的 key，比較不會變。

- 每個素材一張照片：上傳、換一張、旋轉（0／90／180／270）。
- 有區域的素材：在照片上用手指拖出矩形，一次一個區域，可以拖角落微調；座標存成相對比例 `[x, y, 寬, 高]`（與 `video.json` 相同）。
- **開工前先做小實驗**確認精準度（tasks 1.3）。
- 必拍素材都有照片、區域都有座標之前，「產生影片」回 422 並列出缺什麼。

**D7 進度回報。** `render_video` 加一個進度回呼（`integrations/video`）：排版、旁白（第幾句）、段影片（第幾段／共幾段，沿用快取的直接跳過）、疊進度條、混音。工作的 `progress`、`message` 依此更新。

**D8 播放（Q8）。** 成品 mp4 由後端提供網址；前端加 `video_player` 套件，`lesson_video_player.dart` 補上 `file` 來源。

**D9 手機版面。** 單欄、按鈕在拇指範圍、斷點用 `core/layout/`；專案頁顯示「目前在哪一步、下一步做什麼」；進行中的工作顯示進度與說明；失敗時顯示哪一步失敗、原因、可以做什麼。直接做正式頁面（`pages/`），不另做參考畫面。

**D10 驗收環境（Q2）。** 永傑的電腦跑後端與網頁，手機連同一個 Wi‑Fi；身分用開發模式的店員帳號（`X-Dev-User`）。需要：後端與網頁綁定區網位址、CORS 允許手機來源、網頁的 `API_BASE_URL` 指向電腦的區網位址；伺服器上的 ffmpeg 與字型沿用本機的設定。

## Risks / Trade-offs（依嚴重程度）

1. **[手機上拖框不夠準]** → 開工前先做小實驗；不夠準就回來討論（加放大、或換做法）。
2. **[工作會被伺服器重新啟動中斷]** 已知限制。→ 失敗時說明原因，可以重試；快取保留，重試時已完成的段不重做。
3. **[手機照片品質]** OCR 錯字帶進草稿；素材反光、歪斜（第 4 階段才偵測）直接出現在影片。→ 店員在步驟 1、4 看得到結果並可以重拍。已知限制。
4. **[檢查點前不能在手機上用一句話修改草稿]** → 用「重新產生草稿」（沿用照片與區域）。修改頁是檢查點之後一定要做的 MR。已知限制。
5. **[LLM 費用與時間]** → 一個專案同時只有一個工作；工作紀錄留存。
