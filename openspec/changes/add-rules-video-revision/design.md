# Design

## Context

- 規格：根目錄 `影片生產器規格.md` 的產品流程第 6 步與開發階段第 2 階段。
- 第 1 階段：`add-rules-video-maker`（已在本機歸檔，待上傳）、`add-rules-video-script`（#76 審核中）。
- 第 1 階段的限制：每段畫面都畫了全片進度條，所以旁白長度一變，同一章的段都會重新編碼。第 1 階段已決定，第 2 階段的前置項目是把進度條改成最後才疊上去。
- 段資料已經預留 `state`（`status`、`content_hash`、`render`）與 `revisions`（修改紀錄）欄位，第 1 階段沒有寫入。

## Goals / Non-Goals

**Goals**
- 店員用一句話提修改，只有受影響的段被改、被重新編碼。
- 每一次修改都有紀錄，改之前的版本有備份。
- 版型做不到的需求不硬改，而是提供替代做法，並把需求記下來，作為第 3 階段的輸入。

**Non-Goals**：API、資料表、前端（1d）；其他版型、自動檢查（第 3 階段）；拍攝偵測（第 4 階段）；undo 指令。

## Decisions

**D1 進度條最後才疊上去（MR 1）。**
- `Renderer.render(t, progress=True)`：靜態圖照舊畫進度條，方便看版面；段影片編碼時用 `progress=False`。
- 串接成無聲版後，另外產生一條「進度條影片」：只有進度條那一小條（1920 × 進度條高度），逐格畫出填滿的進度。再用 ffmpeg `overlay` 疊到無聲版的對應位置。
- 疊加需要重新編碼整支影片（不能 `-c copy`）。一章約 30 秒，用 `veryfast` 編碼約幾秒到十幾秒，可以接受。
- **重新編碼的品質設定**寫成常數，MR 說明列出：段影片 libx264 `crf 18`、`veryfast`、`yuv420p`；疊加這一步也是 libx264、`yuv420p`，crf 與 preset 依本機量測決定（2026-11-21 永傑要求）。
- **畫質檢查**：external 測試把「串接後、疊加前」的影片與成品逐格比 SSIM（不含進度條那一條），確認二次編碼沒有讓畫質明顯下降；量測數字寫進 MR 說明。
- 行為差異：進度條改成最後才疊，段開頭的淡入（fade）不再蓋到進度條，淡入時進度條保持可見。
- `content_hash` 拿掉 `progress`（全片長度、各章範圍、這段的開始秒數）。只有這段自己的內容、素材、風格、字型、句長改變時，才重新編碼。
- 第 1 階段的測試 `test_narration_length_change_reencodes_timed_segments` 預期「第 1 句變長時第 1、2 段都重做」。這是第 1 階段刻意接受的限制，現在要拿掉，所以預期改成「只重做第 1 段」。依 AGENTS.md 7.5，這是行為依決定改變，MR 說明會寫出理由。

**D2 修改要求的處理（MR 2）。** 指令：

```
revise <資料夾> "情況二的紅框改成金框"                 # 直接套用
revise <資料夾> "情況二的紅框改成金框" --dry-run       # 只看提案，存成 pending.json
revise <資料夾> --apply                                # 套用 pending.json 的提案，不再叫 AI
revise <資料夾> "…" --segment s2                       # 目標不明確時，指定要改的段
revise <資料夾> --choose 2                             # 選替代做法
（上面都可以加 --pages rulebook/en-005.txt：寫入後對被改的段跑涵蓋檢查）
```

1. 讀取 `<資料夾>/video.json`（手寫版或 AI 草稿都可以）。
2. 交給 LLM（`generate_json`）。輸入：修改要求、目前每一段的內容（旁白、字幕、槽位、highlight、label、動作）、版型目前能做的事（版型、槽位種類、五種動作）；有 `--segment` 時註明只能改那一段。指示要求：**沒被點名的欄位原文不動**。
3. LLM 回傳三種結果之一：
   - **可以做**：受影響的段的完整新內容（以段為單位整段取代）、每段的說明，以及每段**被要求修改的欄位**（`requested`）。
   - **超出能力**：原因，加上 1 到 3 個替代做法；每個替代做法都附上完整的新段內容。
   - **目標不明確**：多段都符合修改要求，列出候選段與理由。程式不寫入，印出候選段，請店員用 `--segment` 指定。
4. **超出版型能力的判斷依據**（2026-11-21 永傑決定）：LLM 回「可以做」，但新內容用了五種動作以外的 `do`，程式就把它當成超出能力，再呼叫一次 LLM 取得替代做法，**不走改寫**。schema 不把 `do` 限制成五種，程式才看得到 AI 想用什麼動作。
5. 程式只取代 LLM 列出的段，其他段原封不動。新段的 `segment_key` 必須和原本相同，不能新增或刪除段。
6. 檢查：正式模式的段資料驗證、不用「次」、對照表 `avoid`（資料夾內有 `terms.json` 時）。不通過就帶著錯誤要求 LLM 改寫一次，仍不通過就不寫入，並保留原始輸出。
7. 欄位差異：程式比對新舊段，算出改了哪些欄位；**沒在 `requested` 裡卻被改的欄位另外標「未被要求修改」**，直接套用與 `--dry-run` 的輸出都會列出。超過 2 段被改時，輸出中提醒店員確認。
8. 寫入前，把原本的 `video.json` 備份到 `<資料夾>/revisions/<編號>-before.json`。
9. 寫入後，有 `--pages` 時對被改的段跑涵蓋檢查（見 D8），只顯示警告，不擋寫入。

**`--dry-run` 與 `--apply`**：`--dry-run` 不寫入 `video.json`、不備份，把通過檢查的提案（新段內容、欄位差異、修改要求、當時 `video.json` 的雜湊）存成 `revisions/pending.json`。`--apply` 直接套用這份提案，不再呼叫 AI；`video.json` 在 dry-run 之後有變動（雜湊對不上）時拒絕套用，請店員重跑。

**D3 修改紀錄。** 每段的 `revisions` 新增一筆：

```jsonc
{ "number": 3, "at": "2026-11-21T08:00:00Z", "by": "staff", "kind": "revision",
  "request": "情況二的紅框改成金框", "changed": ["highlights"], "summary": "h_death 的 style 由 red 改為 gold" }
```

`changed` 由程式比對新舊段算出，不靠 LLM 自報。欄位分類：`narration`、`subtitle`、`keywords`、`cues`（各句的對應部分）、`beats`（增刪句子）、`slots`、`highlights`、`labels`、`timing`、`template`、`transition_in`、`source_pages`。`requested` 用同一組分類。修改紀錄另記 `unrequested`：被改但沒被要求的分類。`state.status` 設為 `stale`，表示這段要重做；`render` 成功後改回 `rendered`。

**D4 超出能力時。**
- 不寫入 `video.json`，把替代做法存到 `<資料夾>/revisions/pending.json` 並印出編號與說明。
- 需求記到 `<資料夾>/revisions/requests.json`（修改要求、原因、時間；由程式判斷時記下不支援的動作），作為第 3 階段版型與動作的輸入。
- 店員用 `--choose <編號>` 選一個。選了之後照 D2 第 5–9 步套用，修改紀錄的 `kind` 為 `alternative`，並記下原本的要求。
- `pending.json` 只保留最後一次的提案或替代做法；下一次 `revise` 會覆蓋它。`--apply` 只接受 dry-run 的提案，`--choose` 只接受替代做法，拿錯時說明原因。

**D5 只重做受影響的段。**
- 依 D1，`render` 只會重新編碼 `content_hash` 有變的段。
- 旁白只有改過的句子會重新合成；旁白快取以「TTS 種類＋聲音＋文字」為鍵，第 1 階段已具備。
- `render` 的報告列出這次重新編碼與沿用快取的段。

**D8 寫入後的涵蓋檢查**（2026-11-21 永傑決定）。
- 有 `--pages` 時用指定的頁面；沒有時沿用段資料 `source_pages` 記錄的頁面（`source_pages` 只能是本章的頁），到 `<資料夾>/rulebook/`、上一層的 `rulebook/` 找頁面檔。找不齊就不做，明確印出「這次沒有做規則涵蓋檢查」與原因；檢查失敗時也印同一句（2026-11-21 永傑要求）。
- 規則常常跨段，所以輸入仍是整章的旁白與字幕（沿用 `video_coverage`），但**只顯示和被改的段有關的警告**：問題句在被改的段、或規則的句子編號落在被改的段；完全沒有對應句子的「未涵蓋」規則另列，註明可能和這次修改無關。
- 只顯示警告，不擋寫入；涵蓋檢查的 LLM 失敗或回空清單時，也只印警告。不覆寫資料夾裡的 `coverage.json`（`compare` 會因雜湊對不上標示過期）。

**D6 測試。**
- 單元測試：`FakeLLMProvider` 照腳本回傳。涵蓋：只取代列出的段、不能改 `segment_key` 或增刪段、修改紀錄與 `changed`、未被要求修改的欄位、備份、檢查不通過時改寫一次、超出能力時的替代做法與需求紀錄（含程式判斷的不支援動作）、目標不明確、`--dry-run`／`--apply`、`--choose`、寫入後的涵蓋檢查警告。
- 段快取：改用 D1 的 `content_hash` 後，「旁白長度改變只重做那一段」。
- external（本機）：真 ffmpeg 疊加進度條後，成品在第 t 秒的進度條填滿比例正確。
- 依 AGENTS.md 7.6，`rules_qa` 的測試不需要金鑰；實際呼叫 LLM 的部分在本機驗收。

**D7 兩個 MR。**
1. MR 1（`feature/integrations-video-progress-overlay`）：D1 進度條最後才疊上去。
2. MR 2（`feature/rules_qa-video-revision`）：D2–D5 修改流程。從 MR 1 往下接，或等 MR 1 合併後從 dev 開。

## Risks / Trade-offs

- **[每次輸出都要重新編碼整支影片一次]** 疊加進度條不能 `-c copy`。→ 一章約 30 秒，成本低；換來改一段只重編那一段。
- **[LLM 改到不該改的地方]** → 只取代 LLM 列出的段；`changed` 由程式比對算出並列在報告與修改紀錄中，店員可以看到；改之前有備份。
- **[修改要求很模糊]** 例如「好看一點」。→ LLM 可以回「超出能力」並提出替代做法；指示要求它不要擅自大改。
- **[超出能力的判斷不準]** → 替代做法由店員選；所有「超出能力」的需求都會記錄，之後可以檢討。

## 已決定（2026-11-21 永傑）

1. 修改單位是整段取代。
2. 一次改幾段不設上限，超過 2 段時在輸出中提醒。
3. 提供 `--dry-run`；提案存成 `pending.json`，確認後用 `--apply` 套用，不再叫 AI。
4. 寫入後對被改的段跑涵蓋檢查，只顯示警告（D8）。
5. 指示要求沒被點名的欄位原文不動；欄位差異另外標出沒被要求改的欄位（D2 第 7 步）。
6. 目標不明確時不寫入，列出候選段；五種動作以外的 `do` 走替代做法，不走改寫（D2 第 3、4 步）。
7. MR 1 的說明寫出重新編碼的品質設定，並檢查畫質（D1）。
